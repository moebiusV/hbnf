HyperBNF

Status, 31 October 2026. JSON, TOML and YAML are built and tested in all four backends (TOML against toml-test and tomllib, YAML against the YAML test suite and PyYAML), and are measured against the libraries people use for them, on glibc. C is a family of grammars, each checked against its own era's yacc grammar and compiler: c79 (UNIX/32V's C, run over the 32V source tree itself), c89, c99, pcc99 (what PCC's cgram.y reads), gnu99 (what GCC 4.0.4's reads) and c11; the C parser is also measured against gcc -fsyntax-only and run over the SQLite amalgamation. A grammar chooses the structure its parser builds: the typed tree (layout ast, the default), a flat tape of words (tape, runtime/hbnf_tape.h), or the daemons' own sys/queue.h and sys/tree.h containers (tailq, rb). %emit blocks write the tape by hand where a layout does not fit. The parsers read alternatives that begin alike once, and a ladder of binary operators with one look past its first operand. The code templates are rendered by the project's own Mustache package, HBNF_Template, so libhbnf depends on nothing outside the GNAT runtime. Next: the tape layout for str, bool, flag and the fixed-width numbers and for the Rust, Zig and Ada backends (RFCPLAN.md), C17 and C23 for the C family, the C grammars through LLVM's ORC JIT and lld, the C preprocessor grammar and the typedef context for C, error recovery, grammars for COBOL, ALGOL 68 and C++ (full GLR where they need it, paid for only by the grammar that uses it), and the benchmark of the four backends against each other (the numbers here are the C backend's).

HyperBNF is a grammar language, and hbnf is the program that reads it: a parser generator (a compiler compiler) that emits a parser and its typed tree in C, Rust, Zig or Ada. The name is an homage to the W-grammar and its hyper-rules: a rule may take parameters, and each use becomes an ordinary rule before any backend sees it. It is a superset of BNF, EBNF, ABNF and YBNF (yacc's grammar language).

The design is for anyone who is comfortable reading the RFCs. HyperBNF makes BNF natural and readable the way the RFCs do: a grammar reads like the notation RFCs have used for decades, not like a yacc file with embedded C actions.

It is also a tool for making language models more effective, on one premise: what lessens a person's mental load lessens a model's token usage. A grammar short enough for a person to hold in mind is short enough for a model to read and write cheaply, and the same file gives a program its parser. HISTORY.md makes the case, WHY.md counts the tokens, and step 14 of RFCPLAN.md plans the emitter that would hand the same grammar to a model's decoder.

HyperBNF ships with the basic formats ready to use: JSON, TOML and YAML. Drop one in and you have a parser; the grammar is short, readable HyperBNF, so changing it to fit your own needs means editing a few lines, not learning a generator.

Parameterised rules, back-references and context sets carry what a yacc grammar leaves to hand-written lexer hacks, which is what context-sensitive languages need.

ABNF is the starting point because it is the notation the RFCs actually use: RFC 5234 defines it, RFC 7405 adds case-sensitive string literals, and dozens of newer RFCs specify their protocols in it. Start from the notation people already read fluently, and a grammar is documentation first and a parser second.

The OpenBSD configuration file format was the initial inspiration for developing hbnf, but then that revealed some problems in the parser generator world that looked like they needed solving. The format, the grammar for it and the daemons it was written for are in obconf.md.

Two things

This directory holds two things:

  1. libhbnf, a static Ada library: the grammar reader, the compilability checks and the four emitters (C, Rust, Zig, Ada). Everything hbnf does is in it, and hbnf, the command line, is a thin wrapper over it: argument parsing, finding the templates, and printing what the library returns.

  2. The parser generator, hbnf: read a schema in HyperBNF's ABNF-like notation and generate a parser and its typed tree in C, Rust, Zig or Ada.

    hbnf corpus/json/json.hbnf --backend=c|rust|zig|ada

    --layout=ast|tape|tailq|rb|NAME picks the structure the parser builds (layouts are directories, layouts/NAME/layout.hbnf, found by --layouts=DIR or $HBNF_LAYOUTS), --lint says where an ordered choice | could be a union /, and --no-factor and --no-ladder turn off the shared reading of alternatives that begin alike and of a ladder of binary operators.

    The generator's documents:

    • WHY.md: the grammar and its design choices, for an RFC reader;
    • ABNF.md: the notation against RFC 5234, feature by feature;
    • CHARLAYER.md: character rules, numeric terminals and UTF-8;
    • WIRE.md: octets and bit fields (ttl:8, version@0:4), enum numbers ("icmp"@1), and parsers that also write bytes back;
    • RFCPLAN.md: the plan to compile RFC grammars as written;
    • USENIXSUBMISSION.md: the design paper, with measurements.

  • corpus/sgml/README.md: SGML (ISO 8879), the part a grammar can read: the DTD's declarations, the SGML declaration and the instance's markup; no oracle was available.

  • corpus/json/README.md: JSON in 14 rules, checked against Python's json.
  • corpus/toml/README.md: TOML 1.0 in 46 rules against the ABNF's 124, all 208 valid toml-test files accepted, checked against Python's tomllib.

  • corpus/graphql/README.md: GraphQL (October 2021), the executable language and the type system in 54 rules against the specification's 99, no word reserved where the specification does not reserve it, 145 good and 145 bad files in four backends.
  • corpus/js/README.md: JavaScript (ECMAScript 2023), the Script and Module goals in 151 rules against the specification's 303 productions; semicolon insertion and return/++/=> line-end restrictions by eol; the test262 parser tests and V8 as the oracle.
  • corpus/bip39/README.md: the ten BIP-39 word lists.
  • corpus/bech32/README.md: bech32 and bech32m.

Measurements (bench/README.md says how they are made)

  • environment, headline, toy grammar, hbnf on the toy, yacc, ANTLR and PEG, tree-sitter, the libraries, C against gcc, number conversion, the Haskell parsers, the Raku parsers, the size of the notations, tokens, the corpora with the old node layout and compact nodes (in Rust, Zig and Ada too), the daemons' speed (ntpd, and pfctl against its yacc) and the size of their grammars against parse.y (parsey).

How much grammar. The same language in the published notation and in HyperBNF, with comments, blank lines and hbnf's directive lines left out of both (bench/notation.sh). A symbol is a whitespace-separated word. Mustache is not here because it has no published grammar to compare with.

For C the published grammars are yacc's, counted by their rules alone (the C actions, the declarations and the lexer are left out, which favours yacc, and so are the %left precedence declarations, which spare a yacc grammar the ladder of expression rules HyperBNF writes out), and each is set against the HyperBNF grammar of the C it reads: UNIX/32V's (1979) against c79.hbnf; PCC's against pcc99.hbnf, which is C99, the C11 forms PCC's grammar has, and its subset of the GNU extensions; and GCC 4.0.4's against gnu99.hbnf, C99 and the GNU extensions its grammar reads. Each C grammar is counted alone, and then with the token rules that do the lexer's work. For YAML the published side is the specification's own productions. HyperBNF puts alternatives on one line, so it takes far fewer lines than any of them. Against the yacc grammars of 32V, PCC and GCC it takes fewer rules, and about as many symbols or fewer (PCC's, within half a percent); in characters it is larger than 32V's and PCC's, because its rules are named as the standard names them and a yacc grammar's are short, and smaller than GCC's.

JSON, TOML, YAML and XML against the parsers people use

The same four documents against the parsers people use for each format: the popular C, C++ and Rust libraries, built from one source with the same flags, and the parsers that Python and Node programs call. All of it runs on glibc (Debian). The libraries were picked by GitHub stars and package downloads, limited to what Debian packages or ships as a single file. For XML they are expat (the base of Python's pyexpat and ElementTree, of Firefox and Apache), libxml2 (the base of lxml and xmllint), pugixml, TinyXML-2 and RapidXML (the original 1.13, unmaintained since 2009), the Python and Node parsers (ElementTree, lxml, the raw xml.parsers.expat, fast-xml-parser and sax), against the typed tree of corpus/xml/xml.hbnf. The XML table has a column that says what each parser hands the program, because they differ most there: expat, libxml2's SAX2 interface, pyexpat and sax are event parsers that build nothing (the expat row that copies names, attributes and text into arrays shows the price of a cheap tree), pugixml, TinyXML-2, RapidXML, libxml2, ElementTree and lxml build a DOM, and every XML parser has to find the same elements, attributes and text as ElementTree or its row says check failed. The last column says whether the parser is a conforming XML 1.0 parser: how many of 34 documents that each break one well-formedness constraint it refuses (and, not shown, whether it accepts 11 well-formed ones), by bench/xml-conformance.sh, which keeps its result and checks a parser again only when its version, the case set or hbnf's grammar changes. expat, libxml2, ElementTree and lxml refuse all 34; hbnf's grammar does since 2026-11-04; pugixml (8), RapidXML (7), TinyXML-2 (9), sax (20) and fast-xml-parser's parse (0) are marked with a red cross, because they accept content XML forbids, and their times are not like for like with the others. What each builds differs: the C++ and Rust libraries, Python, Node and the YAML parsers produce their own value types, simdjson is its DOM API, and hbnf builds the typed tree its grammar describes. Peak RSS is the whole process, input included, and the last column shows it as a multiple of the input. The numbers are bench/libs.sh.

On TOML the generated parser is the fastest by a wide margin. On JSON the parser that writes a tape (corpus/json/json-tape.hbnf) is close to the SIMD parser simdjson, uses less than half its memory, and the typed-tree parser is ahead of everything else; on YAML both are ahead of rapidyaml, libyaml, libfyaml, js-yaml, yaml-cpp and PyYAML, which build generic node trees. The rows that say %emit tape build a flat array of words and no tree (runtime/hbnf_tape.h); the others build the typed tree the grammar describes. --layout=tape makes any grammar's parser write such a tape, with no %emit in the grammar. A program reading a tape converts a number or string with runtime/hbnf_scalar.h, which bench/scalar.sh compares with fast_float.

Naming

  • hbnf: the parser generator and compiler compiler. Reads a grammar, emits a parser in C, Rust, Zig or Ada. Also the command line, the Alire name, and the project file (hbnf.gpr).
  • libhbnf: the static Ada library (libhbnf.a, project libhbnf.gpr) that the hbnf command line wraps. A C reference implementation, if there is one, will not take this name for its shared library.

Building

Pure Ada on the GNAT runtime, no C dependency. The code templates are rendered by the library's own Mustache package, HBNF_Template (hbnf_template.ads); it reads a template with the parser hbnf makes of grammars/template.hbnf (hbnf_template_syntax*, regenerated by scripts/gen-template-syntax.sh, tested by tests/template.sh).

gprbuild -P libhbnf.gpr -p -XLIBRARY_TYPE=static
gprinstall -P libhbnf.gpr -p --prefix=/usr --sources-subdir=include/hbnf

Packaged for Alpine by the ada-on-alpine aports overlay as testing/hbnf.

Build through the project files, not gnatmake -I.. gprbuild keeps its own object directory; gnatmake -I. -D <tmpdir> compiles into the temp directory but gnatlink takes hbnf.ali from ., so a stale .o left in the source directory wins the link and the build reports success while running yesterday's code. Those files are .gitignored, so git status stays clean while it happens. If you must use gnatmake, rm -f *.o *.ali first; tests/e2e.sh does that for you and refuses to run against a binary older than its newest source.

Contributing

Ada is written in the functional style in STYLE.md: constants by default, expression functions, no out/in out parameters, loops replaced by 'Reduce and comprehensions, and side effects kept at the edges. Read it before contributing.
