JavaScript (ECMAScript 2023) in HyperBNF

js.hbnf (the syntax: statements, expressions, patterns, functions, classes, modules; 83 rules) and js-tokens.hbnf (white space, comments, names, numbers, strings, templates, regular expressions; 68 rules) are the grammar of ECMA-262, 14th edition (clauses 12 to 16 and the parts of Annex B that real code uses). js-unicode.hbnf is a table generated by idtables.py from the Unicode 16.0.0 data: the code points above 127 that may start a name and may continue one. The first rule is script (the Script goal); --root=module reads a Module and --root=function-body the body of a function, which is what the code of an attribute such as onclick="..." is.

hbnf corpus/js/js.hbnf --backend=c > js.c                       # a Script
hbnf corpus/js/js.hbnf --backend=c --root=module > jsm.c        # a Module
hbnf corpus/js/js.hbnf --backend=c --root=function-body > jsf.c # the code of an event handler

Where the saving is: the parameters. Yield, Await, In, Return and Tagged are written on 130 of the specification's productions; here In is a parameter of the expression rules (expression(I), binary(N, I)) and Return of the statements (statement(R)), Tagged is the argument of template(E), and Yield and Await are not parameters at all (see below). The ten binary levels and their lists are binary(N, I); the binding patterns, the assignment patterns and the parameter lists are one pattern(T) and list(E); a function, a method, a getter, a setter and an arrow function share parameters(C) and function-block; a class and an object literal share method(N); var, let, const and the for heads share binding(I). The specification writes each of those again, with its own name.

The hard parts

/ and }. A regular expression is a primary expression: it is read where an operand is expected, and / is a division only after an operand, so there is nothing to decide. The pieces of a template are tokens (tpl-head, tpl-mid, tpl-tail), and template(E) is tpl-head expression *( tpl-mid expression ) tpl-tail, so the } that ends a substitution is the first character of the next token, and a } that ends a block is a }. A tagged template (E is esc-any) may hold any escape, an untagged one only the legal escapes (esc-tpl).

Automatic semicolon insertion and the restricted productions. ws skips line ends, and a lookahead (&x, !x) is evaluated after the blanks are skipped, so no lookahead can ask whether the blanks it skipped held a line end. The test that sees the position a token ended at, before the blanks after it, is eol (bol is the other). So:

  • every token that can end a statement (identifier, number, string, regex, a template's last piece, ) ] } as rpar rbrk rbrace, ++ -- as incr, this null true false, the keywords return break continue yield debugger) ends with *inl: the blanks and comments on its line;
  • ends(X) is X ";", or X and a lookahead for }, or X and the end of the input, or X eol: a line end follows at once;
  • eol is the position after X only if X's last element is not optional or repeated (the parser skips the blanks before an element that can be empty, and the position is then after them), so a rule that can end a statement is written a b | a and not a [ b ]: binary(N, I), conditional, assign, expression, lhs, update and the others are;
  • return, break, continue and yield are ends(K) or ends(K operand): when a line end follows the keyword the first alternative takes it; throw and async are tokens that fail when a line end follows (nolt);
  • x ++ is lhs !incr-ahead | lhs eol | simple-target incr: a ++ after a line end is a prefix ++ of the next statement;
  • => is read by arrow-id and arrow-rpar: the name or the ) and, on the same line, the arrow.

What is not seen: a multi-line comment that holds a line terminator and is the only line end between two statements is not counted as the line end (a /* newline */ b), and U+2028 and U+2029 are white space and not the line end that ends a statement (eol sees LF and CR). HTML-like comments are in ws (Annex B): <!-- anywhere, and --> after a line end, or as the first thing in a script.

The cover grammars. PEG is ordered: (a, b) => x is tried before (a, b), async (x) => y before the call async(x), and a pattern of an assignment ([a, b] = c) is read as an expression first and, when = follows, as a pattern (assign): the rest of the specification's cover grammars (CoverInitializedName, CoverParenthesizedExpressionAndArrowParameterList) is that. The target of an assignment is a pattern(assign-target) or a simple-target: an identifier, a member, a call with a member after it, or those in parentheses; 1 + 1 = 2, [v] += x, ++1 and ({a: 1} = x) are refused by the grammar, not by a later check.

Contextual keywords. reserved is the specification's list; async, await, yield, let, of, get, set, static, from, as, target and meta are words of a construct where one is expected and names elsewhere. yield and await are the exception to exactness, see "Not in the grammar". The keyword boundary needs a rule that uses word (plain-word = word - reserved); see "Findings".

Compactness. See "Where the saving is".

Covered

The Script goal and the Module goal: identifiers with \u escapes and the Unicode 16 ID_Start/ID_Continue as ranges; numeric literals (separators, bigint, hex, octal, binary, the legacy octal and 08.5 forms of Annex B), strings (all escapes, line continuations, U+2028 and U+2029), templates, regular expression literals and flags (the body is read, not compiled), comments, hashbang; every statement (labelled, with, for await, for in all its heads, Annex B's function in if and in a label), functions, generators, async functions and async generators, arrow functions with all parameter forms, classes (fields, private names, static blocks, accessors, computed keys, #x in o), destructuring in declarations, parameters and assignments, spread and rest, the full expression ladder (**, ?? not mixed with ||/&&, ?., logical assignment, new.target, import.meta, import(), tagged templates), and import and export declarations.

Not in the grammar

  • Early errors, the static semantics of clauses 13 to 16: a duplicate let, break or continue outside a loop, an undefined label, a regular expression that does not compile, a repeated parameter, super outside a method, new.target outside a function, a private name that is not declared, a call as the target of =, \u escapes that are not name characters, const without an initializer outside a for, strict mode (the grammar is of the sloppy Script and keeps no mode: octal escapes and with in strict code, eval as a target, ...). V8 reports them as SyntaxErrors; the test marks them L and either answer is allowed.
  • yield and await as names or operators by context. They are an operator wherever an operand can follow and a name elsewhere (yield-form, unary-op), whether or not the function is a generator or async. A valid program is read as the specification reads it; yield 1 in a plain function, await x outside an async function, and the module's top-level await as a name, are accepted. Exactness would need Yield and Await as parameters of every expression rule (the generated parser twice or four times the size).
  • Module goal differences: HTML-like comments and legacy octal literals are Script features; the module's ws is the same.
  • The import.meta and import declarations are accepted in the wrong goal (import.meta in a Script).
  • A name that has both a \u escape and a non-ASCII letter (℘℘): the table of letters cannot share a scanner with the escape (the generator does not finish), so the escape is read only in names of ASCII letters.
  • /x/ is read, not compiled: /(/ is a regular expression literal.

In an island

Section 27 of CONTEXTS.md: this grammar is to be an island in HTML, include "../js/js.hbnf" as js and js.script after <script>. The rule is script; for an attribute value (onclick="...") it is function-body (a rule of its own, so --root=function-body generates it and a host calls js.function-body). Nothing in the grammar refers to a host, and its ws is the rule ws of the tokens file. It cannot be included today: include ... as js gives

hbnf: rule `no-expression-start` is not defined in grammar `js` (it is used by `js--statement(R in "fn" | "top")`) ...

the island limit of CONTEXTS.md 26.27 (a lookahead on a guest rule), and the next one would be the guest's own ws rule (the white space of a scope is the host's or none). What the host must also do: HTML ends a script at the first </script, which no JavaScript token may hold and which JavaScript does not know; and <!-- in a script (Annex B) is a comment to JavaScript.

Findings: what the notation or the generator could not do

Found while writing this grammar; none is fixed, and none is in CONTEXTS.md 26 (items 27 to 33 there are the HTML grammar's). Each has the smallest grammar that shows it.

  1. A lookahead is evaluated after the blanks are skipped; only bol and eol see where the previous element ended. So a rule for the blanks and a lookahead for it cannot ask whether the blanks held a line end: program = "a" &nl "b", nl = *blank LF, ws = *( 0x20 | 0x09 | LF ) refuses a, LF, b.
  2. A rule that ends in an optional or repeated element ends after the blanks: program = e eol "b", e = id *tail, tail = "," id, ws = *( 0x20 | LF ) refuses a, LF, b; e = id 1*tail | id accepts it. The parser skips the blanks before an element that can be empty, and a repetition of none leaves them skipped. The ladder optimization of the C backend (a = b *( op b ) and its levels) leaves the position after the blanks too.
  3. Shared beginnings are not factored in a rule that has a first-byte dispatch (alternatives that begin with different keywords), or when the rest of an alternative begins with a block (eol, !x, &x): x = id ";" | id eol parses id twice. The cost of a failing parse is then a product through the nesting; the grammar keeps its a b | a rules free of keyword alternatives for that reason (assign and exponent are rules of their own).
  4. A rule that ws reaches and that holds a lookahead is checked as a plain rule: no repeated group (*( a | b )), no string literal in the lookahead's operand (ws = 0x20 | nl, nl = 0x0A !pp, pp = "+" is refused, pp = 0x2B is not), no bol in a group, no lookahead inside what ws repeats. The message, the whitespace rule ws` is not a rule of characters ... but, stops after "but" and does not say which rule. The same ws passes in a file with whitespace none. So ws` could not say "a line end that ++ or => follows is not white space".
  5. A choice of about 700 ranges, followed by anything, is copied for each alternative: x = id-start *id-continue (661 and 769 ranges) is 126 MB of C and minutes of gcc; and one alternative of several characters (an escape BS 'u' 4HEXDIG) in the same repetition as the table makes the generator not finish. ident = &start 1*cont, a lookahead and a loop, has neither (and a table of non-ASCII letters in a loop costs one test of each range for every character of a name, which is why a name of ASCII letters is read by a rule without the table).
  6. Keywords are on only when a rule uses word or atom: defining word is not enough (the generator looks at the elements of the rules). Without it every letter-led literal matches the front of a longer word, in a lookahead (!"class" refused className), in an enum (reserved = "in" | ... matched the front of inx) and in a sequence ("new" read newValues), and nothing warns. program = "in" id, id = ALPHA *ALNUM, word = 1*ALNUM (never used) accepts inx; with id = word - reserved it does not.
  7. Zig: the time of the generated parser grows by a factor of about 3.5 for each level of nesting of brackets or parentheses, where C is linear: x = [[[[[[[[1]]]]]]]]; takes 22 s with Zig 8 deep and 6 s with 7 (debug build, as tests/suite.sh builds it); f(function () { f(function () { ... x }) }) with a line end after each ) and no ;, 5 deep, takes minutes. C reads both 16 and 22 deep in a millisecond. The tests keep the nesting at 4 or less.
  8. ! and & take no code point: program = "a" !0x7B "b" is refused ("looks at a literal, a rule or alternatives of those"); a rule (lbrace = 0x7B) is needed (CONTEXTS.md 26.1 makes 'c' a literal).
  9. No way to say "this token takes the blanks of its line" once: every token that can end a statement says *inl itself (bare(K), nolt(K), rpar, rbrk, rbrace, incr, identifier, number, string ...), a dozen rules that a notation for the position after a token would not need.
