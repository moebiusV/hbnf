RFC 5234, Appendix B.1: the core rules

rfc5234-1.bnf is the sixteen core rules, verbatim. rfc5234-1.hbnf is the same text with one line added, dialect abnf. <id>.vectors/ holds the inputs each rule must accept and refuse; tests/rfc.sh runs both files on them.

What hbnf says to the RFC's text

Nothing. hbnf rfc5234-1.bnf --abnf --root=RULE compiles every rule as written, including the ones that write /: BIT = "0" / "1" and `HEXDIG = DIGIT / "A" / ... are one code point an alternative, and LWSP = *(WSP / CRLF WSP)` is two alternatives that never match the same text (WSP is a space or a tab, CRLF begins with a carriage return), so ordered choice is the union (RFCPLAN.md decision 1).

Why abnf

hbnf's defaults are not ABNF's. Blank space is skipped between the elements of a rule, where ABNF skips nothing and writes a space where one counts (without that, SP could never match). A string is case-sensitive, where ABNF's is not (HEXDIG would refuse a). A backslash in a string starts an escape, where in ABNF it is a backslash ("\" is one). --abnf on the command line, or the line dialect abnf in a file, says the file is in RFC 5234's notation and sets all three.

What the vectors say about the text itself

OCTET = %x00-FF is eight bits in ABNF. hbnf reads its input as UTF-8 and matches code points, so OCTET matches a code point up to U+00FF, which is one byte only for ASCII. That is a difference between the notations, not a bug in the rule; a grammar over bytes is the binary layer (RFCPLAN.md step 5).
