The wire layer: octets, bit fields and enum numbers

The notation that reads a configuration file reads an Ethernet frame too, and the generated parser takes a buffer. There is no binary mode and no separate file type: a field of N bits (ttl:8) is an element like a literal or a rule name, and a rule that holds one is a bit rule. A file may hold text rules and bit rules side by side (a bit rule can read the numbered words of a text rule as its bits: bitsof, below). This is RFCPLAN.md step 7b. Status: the C, Rust, Zig and Ada backends read and write bit rules (the writing direction is the same grammar). Enum numbers ("icmp"@1) work in all four backends already. What is not built is a text element and a bit field in one rule ("GET " len:16 payload:[len]); see the end of this page.

; IPv4 (RFC 791): one 32-bit word to a line.
ipv4 = version@0:4 ihl:4 tos:8 total_length:16
       identification:16 flags:3 frag_offset:13
       ttl:8 protocol:8 header_checksum:16
       src:32
       dst:32
       options:[ihl*4 - 20]
       payload:( ?(protocol == 6) t:tcp | ?(protocol == 17) u:udp | rest:*u8 )

The files tests/wire/net.hbnf (Ethernet, ARP, IPv4, IPv6, TCP, UDP) and tests/wire.sh (byte fixtures for each, read and written back) are the worked examples. So is tests/wire/segwit.hbnf, the data part of a bech32 address (BIP-173, BIP-350): 5-bit symbols, a witness program whose octets start inside an octet, padding that must be zero, and rules on the program's length:

include "bech32.hbnf"
doc = segwit
data = 1*bech32-symbol
segwit = words:bitsof(data)
         version:5 ?(version <= 16)
         program:[(remaining - 30) / 8]
         ?(len(program) >= 2 && len(program) <= 40)
         ?(version != 0 || len(program) == 20 || len(program) == 32)
         pad:bits(align) ?(pad == 0)
         checksum:30

It reads the five published valid addresses to their version and program, and refuses six made to break one rule each. The checksum is read, not yet checked (see the end of this page).

Text and bit rules together

A grammar may hold both, and a rule of either kind may name one of the other. The C backend makes one parser for the lot: the bit rules are read from the text parser's own state, at its position (an octet and a bit offset inside it), with its error record and its arena, by functions with the same signature as the text rules', so a call goes either way:

prefix none
whitespace none
msg = "PKT:" frame ";"          ; a text rule naming a bit rule
frame = len:8 body:[len]        ; a bit rule
include "common.hbnf"
doc = "REC:" record
record = kind:8 label           ; a bit rule naming a text rule
label = 1*ALPHA

parse_text on PKT:\x05hello; gives a msg whose frame has len 5 and a body of five octets; on REC:\x07abc, a doc whose record has kind 7 and label abc. The text of a text rule is octets read as UTF-8, and an octet is eight bits from any bit: after a 3-bit field (flag:3 label) the text is read from bit 3, the generated reader working on a copy of the rest shifted to that bit. Because that is most often a missing field or padding, hbnf prints one note to standard error when it generates such a parser, naming the first rule where text follows fields that end inside an octet; it is only a note. The tests are tests/wire/mixed*.hbnf.

Zig reads these too, and so do Ada and Rust (text rules and bit rules in one grammar, a text and a bit field in one rule, and %emit and emit_bits_<rule> for the bit rules; Zig also has bitsof anywhere in a rule over any text rule), in the same hosted way: the bit rules are read from the text parser's own input and position, and a bit rule that names a text rule with structure has the text parser read it (bnf_sub). %action works in them too: after the whole text has been read, a walk over the tree (children first) runs the action of each bit rule it holds, as C does; mixed5 is the test, one grammar per language. --writer is built for them in Zig, Ada and Rust too, for rules without alternatives (see below). bitsof anywhere in a rule, over any text rule, works in Zig, Ada and Rust. In Rust the text parser is over bytes (parse_text(&[u8])), so a bit rule can hold any octet; in Ada the Parser child's spec gets Emit_Bits_<Rule>. Their tests are mixed, mixed2, mixed3, mixed4, mixed6 and segwit_in, in tests/wire.sh for each of the three.

What is not built for it: the first rule must be a text rule (a grammar whose first rule is a bit rule is read as bits alone, and says so if it names a text rule); --writer writes a whole mixed document: write_<root> writes the text rules, and a bit rule in them by its own emit_bits_<rule> (which runs its %emit), its octets going into the text as they are (a bit rule that does not end on an octet is refused when written; tests/wire/mixed7). A bit rule still writes a text token it holds but refuses a text rule that is not a token; and only C has it. An %action on a bit rule runs after the parse, its HBNF_FAIL fails the parse, and its HBNF_WARN warnings are read with hbnf_warnings () and hbnf_warning (i). A bit rule that holds a text rule by value is not built.

A text element and a bit field may stand in the same rule (req = "GET " len:8 payload:[len] %d13.10). The reader splits the rule into runs, each run of bit fields and each run of text becoming a hidden rule req_1, req_2, req_3, and req a sequence naming them; the fields are reached through them (out.req_2.len). A group that holds both kinds is refused, with a message saying to split it. In a rule that holds bit fields a number is a constant as wide as its digits (0x05), so the text there writes its code points the ABNF way, %d13.10; in any other rule of hbnf's own notation a code point is 13 10.

Why these two characters

char means precedent
:a width: ttl:8 is 8 bits C's bit-field (unsigned ttl : 8), Erlang's bit syntax (<<Ttl:8>>); and, at the start of a rule, the definition: Forth's : name ... ; and the label in assembly
@a place: version@0:4 is 4 bits starting at bit 0 "at": Ada's representation clause (F at 0 range 3 .. 7); BLISS and IMP72 give position and size together (A<p,s>)

Both count from zero, as C and IMP72 do (IMP72's arrays start at zero and its bit fields A<B,C> count from the right). The direction follows the RFCs, not IMP72 or the hardware manuals: bit 0 is the most significant bit, the leftmost in a packet diagram.

They never clash. A rule's : is the first : after a name in column 1 (a rule's continuation lines are indented), and every other : is a width glued to the name before it. @ also numbers an enum literal (below), where "at" means the same thing: at this value.

A field

write meaning
name:NN bits, 1 to 64. The first field is in the most significant bits, the way an RFC's packet diagram reads; fields that do not fill an octet share it
name:16le, name:8s, name:32slelittle-endian (le; be is the default), signed (s). Little-endian needs a whole number of octets
name:u16, name:i32lethe same, spelled as a type
name@K:NN bits that must start at bit K of the record (bit 0 is the most significant bit of its first octet). It writes nothing new; it checks the author's arithmetic against the RFC. hbnf proves it when the fields before it are fixed, and the parser checks it when they are not
name:[expr]expr octets: a slice of the input (a copy if they start inside an octet)
name:*u8all the octets that are left
name:bits(expr)expr bits (at most 64)
0x0800, 0b101a constant, as wide as its digits: 0x0800 is 16 bits, 0b101 is 3. A decimal number has no width, and is refused with that reason
name:rule / rulea nested record of that rule (a bare rule names the field rule)
name:*rule, name:2*4 rule, name:(n)*ruleany number, 2 to 4, exactly n records of that rule
name:( a \| b \| c )one of several; the field has a kind (1, 2, 3) and the alternative's fields
?(expr)a condition. At the start of an alternative it is a guard (the alternative is taken only if it holds); between fields it is a check (the read fails if it does not). ?(expr) "words" is a check whose failure says those words

A rule that is a list of constants (ethertype = 0x0800 | 0x0806 | 0x86DD) is a value set. A field named for it, or of its type, must be one of those values: ethertype:16.

Numbers. Wherever a number is taken (an enum value "x"@N, the bit a field starts at, a width, a repeat count, a constant) it may be written in decimal, 0x hex, 0b binary or 0o octal: a number is a number. A constant's width is its digits (4 bits to a hex digit, 3 to an octal digit, 1 to a binary digit); a decimal number has none. tests/numbers.sh checks every spelling at every place.

Expressions

expr is C's integer arithmetic: + - * / % << >> & | ^ ~ !, comparisons, && ||, parentheses, decimal and 0x numbers, over the fields read earlier in the same record (options:[ihl*4 - 20]), remaining, the number of bits left in the input, len (field), the number of octets in a field read as name:[n] or name:*u8, and align, the bits to the next unit boundary (bitsof, below; a message that ends in a partly filled unit says pad:bits(align)). Division by zero is 0, and a shift count is taken mod 64. Using a name that is not a number read before that point is refused, with the names that are.

Names

A field or rule name becomes an identifier in the generated code: a hyphen is written as an underscore there (total-length is total_length), as in the text backends, and an expression refers to it with the underscore (a hyphen subtracts). A name that is a keyword of the language, or one the generated code keeps for itself, is refused with a rename to try (int:8).

The C API

bool parse_bits  (const uint8_t *buf, size_t nbits, T *out, char *err, size_t errsz, size_t *at);
bool parse_bytes (const uint8_t *buf, size_t len,   T *out, char *err, size_t errsz, size_t *at);
bool emit_bits   (const T *in, uint8_t *buf, size_t cap, size_t *nbits, char *err, size_t errsz);
bool emit_bytes  (const T *in, uint8_t *buf, size_t cap, size_t *n,     char *err, size_t errsz);
void free_arena  (void);

T is the first rule's type. Reading uses the whole buffer or fails and says where (at is the octet) and why (ethernet.src: needs 48 bits, 32 left). Octets are slices of the input; the few that start inside an octet are copied into an arena that free_arena releases.

Writing is the other direction, from the same grammar. With buf NULL it only counts; *n is always the size the message takes, so the usual call is twice. A value that does not fit its field, a length that disagrees with the octets it describes, a value outside a value set, or an alternative whose guard does not hold is an error that names the field, not a silently wrong message. A width that depends on remaining cannot be written: a writer does not know the size of a message it has not written.

Text: a message written in words, bitsof

Bytes are not the only way a message is written. A bech32 address spells 5 bits with each of 32 characters; a BIP-39 mnemonic spells 11 with each of 2048 words. The text is a decoding of the bits, the way UTF-8 is a decoding of octets. A bit rule says so with a field:

include "bip39/english.hbnf"        ; bip39-word, bip39-space: numbered literals
doc      = mnemonic
phrase   = bip39-word *( bip39-space bip39-word )
mnemonic = words:bitsof(phrase)
           ?(remaining % 33 == 0 && ...)
           entropy:[remaining / 33 * 4]
           checksum:bits(len(entropy) / 4)

words:bitsof(phrase) reads the text rule phrase as text, takes the number of each word in it (its place in the list, or "x"@7) as W bits, W being what the largest number needs (11 for 2048 words, 5 for 32 symbols), and the **rest of the rule reads those bits**, as it would the bits of a buffer: remaining is the bits that are left, align the bits to the next word boundary. When the rule ends every bit must have been used, and the input goes on after the text. Writing runs the other way: the fields are written as bits, then spelled as the words, joined by whatever the text rule puts between two (the blank of bip39-space). grammars/bech32.hbnf is the 32 symbols; grammars/bip39/ the ten word lists.

The text rule is the grammar of the text, so a misspelt word, two blanks or a trailing blank are refused by it, with its messages; an error in the bits says where in the words ((at unit 12)). The generated parser is the text parser:

bool parse_text (const char *text, T *out, char *err, size_t errlen, size_t *line, size_t *col);
bool emit_bits_mnemonic (const mnemonic_t *in, uint8_t *buf, size_t cap, size_t *nbits, char *err, size_t errsz);

the second writes the text, as octets (*nbits / 8 of them). The tests round-trip the five published segwit addresses and eighteen mnemonics (the BIP-39 test vectors among them), and generate each mnemonic from its entropy alone, the checksum worked out by %emit. The phrase's own tree is not kept (its words are the bits). Rust, Zig and Ada read bitsof too, in the form the segwit grammar has: a first rule that only names the bit rule (doc = segwit), whose first field is the bitsof, and a text rule that is just the words joined by one separator (1*word, or word *( sep word )). They give parse_text and emit_text (Parse_Text and Emit_Text in Ada) with the same messages as C, including (at unit N). In a grammar that mixes text rules and bit rules (above), bitsof can stand anywhere in a bit rule, over any text rule (segwit_in is the test). The tests are segwit in tests/wire.sh, one driver each, with the same expected output as C, and the BIP-39 mnemonic (see Code, below).

Code: actions, emitters, and the library they call

A wire grammar holds C in three places, none of which hbnf reads or rewrites:

  • { code } before the first rule is the preamble, after the last rule the epilogue: copied as they stand. The preamble is where #includes and prototypes go; the epilogue is where the functions the actions call are defined.
  • %action{ code } at the end of a rule runs on that rule's record, as n, after the whole read has succeeded, children before parents. It never runs during the read, so an alternative that is tried and given up cannot have run it (the rule %action has in a text grammar). n->field are the typed fields; HBNF_WARN ("text") adds a warning to the result (out->warnings[], out->nwarnings, on the first rule's record) for a message that is valid but unusual; HBNF_FAIL ("text") fails the read, naming the rule.
  • %emit{ code } runs when the record is written, before its fields are, on a copy of it as n: it fills in what is computed (a checksum), and the caller's tree is not touched. HBNF_EMIT_FAIL ("text") fails the write. (In a text rule that declares a value, name :: type = ..., %emit is another thing: it runs during the read, in the C backend only; grammars/README.md, "Values at recognition".)

Rust, Zig and Ada have both, written in their own language: the grammar says language Rust (or Zig, Ada), and a grammar in another language is refused with a message saying so. The code is the same four places, and the names are the language's:

C Rust Zig Ada
the record in an %actionn->fn.f (&T) n.f (*const T) N.F
warn HBNF_WARN ("..")hbnf_warn!("..")h.warn("..")Hbnf_Warn (H, "..")
fail the read HBNF_FAIL ("..")hbnf_fail!("..")return h.fail("..")Hbnf_Fail (H, "..")

The preamble is at the top of the file (Ada: the context clauses of the body, with ...;) and the epilogue after the rules (Ada: before the readers, because Ada declares before it uses). Their tests are mnemonic_rust.hbnf, mnemonic_zig.hbnf and mnemonic_ada.hbnf: BIP-39 with OpenSSL's SHA-256 in Rust (linked as libcrypto), Zig's std.crypto and GNAT's GNAT.SHA256, all with the same output (mnemonic_ports.expected).

The action is the semantic member of the family and the emitter the generative one. Warnings are collected in static storage, so a parser that has actions is not reentrant.

Library functions

A checksum is a function in a library somebody else wrote and tested, and an action calls it by its own name: hbnf neither wraps nor reimplements it. The grammar's preamble includes the header, and the program that uses the generated file links the library:

to compute call header link
CRC-32, Adler-32 crc32 (0, buf, n), adler32 (1, buf, n)<zlib.h>-lz
SHA-256 SHA256 (buf, n, out)<openssl/sha.h>-lcrypto
bech32 / bech32m bech32_decode (...)corpus/bech32/segwit_addr.h (Pieter Wuille's reference, MIT) its .c

Where nothing standard exists, the format's own arithmetic lives with its corpus: corpus/bip39/bip39.h has bip39_checksum, the first n/4 bits of the SHA-256 of n octets of entropy. The BIP-39 grammar checks its checksum on reading and computes it on writing:

{ #include "bip39.h" }
mnemonic = ... entropy:[remaining / 33 * 4] checksum:bits(len(entropy) / 4)
  %action{
      if (bip39_checksum (n->entropy.ptr, n->entropy.len) != (unsigned)n->checksum)
          HBNF_FAIL ("the checksum does not match the words");
  }
  %emit{
      n->checksum = bip39_checksum (n->entropy.ptr, n->entropy.len);
  }

so a mnemonic is generated by setting entropy and calling emit_text. The test reads eighteen phrases (the published vectors among them), refuses two wrong checksums, and generates all eighteen from their entropy alone; it is skipped, with a message, where OpenSSL's header is not installed.

Enum numbers

A rule made only of literals is an enum. Its values are 0, 1, 2 ... in the order written; "literal"@N gives one its own number, as NAME = N does in C, and an alternative without one is the one before plus 1:

proto = "icmp"@1 | "tcp"@6 | "udp"@17 | "sctp"@0x84 | "other"

declares icmp 1, tcp 6, udp 17, sctp 132, other 133 in C, Rust, Zig and Ada (an Ada representation clause, a Zig enum(u8), a Rust discriminant). The numbers must fit 31 bits and be distinct. Only a rule of plain literals can have them.

A word list is an enum, and the number of a word is its place in the list. When the author writes words in a union ("act" / "actor") hbnf matches the longer word first, and keeps the values in the order written: the index of actor is where the list has it. That is what BIP-39 needs; corpus/bip39/ holds the ten official 2048-word lists as include files (include "bip39/english.hbnf"), and tests/wire.sh reads every word of every list back to its line number. A union of plain words is a sort, not a search.

What is not built yet

  • --writer for Zig, Ada and Rust writes a whole document of text rules and bit rules (write_<root>, Write_<Root>), as C does: rules with alternatives (and list entries that are groups with them) record the one they took and the writer follows it, left-recursive lists, a root that is only another rule, a newline after each statement, and the layout hook (Layout, a pretty-printer's say). Not written: an alternation inside a group (C does not either). Zig returns error{Parse} with the octet and message through a pointer and takes an allocator, best an arena. Ada writes the specification and body in one file (gnatchop splits it), with Ada.Containers.Vectors for octets and entries and a record with a variant part for a choice (--package=NAME). A language line in a grammar says which language its code blocks (preamble, epilogue, %action, %emit) are written in, C unless it says; the Rust backend reads grammars without code until %action/%emit are done for it.
  • Units. A field's width is in bits and a string is an array of units, but a unit is not always a bit: an octet, a code point and a machine word (9-bit bytes, 36-bit words) are different things, and the notation should say which. The design: a number may carry a unit, b bits, B bytes, c code points, W words, and a file may say how big its byte and word are (byte 9, word 36). @Off:Len is then a slice of any array of units, strings included: name@4B:4B is 4 bytes from byte 4, and name@4:4 is 4 bits from bit 4. Without a suffix the unit is bits for a bit field and code points for a string.
  • Layout records. A record in which every field says where it is (flags@0:3 id@3:13) is a register layout, read in any order with gaps and overlaps. Where only some do, @ is the check described above.
  • A bech32 address's human-readable part. Its checksum covers the part before the 1 (bc) as well as the data, and parse_text reads only the data symbols, so the segwit grammar reads the checksum but does not yet check it. The library can (hbnf_bech32_verify); the grammar needs a way to bring the bc in.
