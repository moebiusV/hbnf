One notation for daemon configs and RFC grammars — the plan (working note)

Agreed 2026-09-28. The goal: paste RFC 5234-family ABNF and get a working parser, and make the nine daemon grammars smaller, clearer and more coherent on the way. There is one parsing model, not two profiles, and the generated parsers stay recursive descent, linear in their input, with no unbounded backtracking.

Where the tree stands, and what this plan builds on: CHARLAYER.md (numeric terminals, 'c' literals, ascii.hbnf, UTF-8 scanners in all four backends). Where the notation differs from ABNF today: ABNF.md §4.

Corpora

Two validation corpora, both exercised every step.

Daemon corpus. The nine OpenBSD daemon grammars (bgpd, dhcpleased, httpd, ldpd, ntpd, pfctl, relayd, snmpd, unwind), each derived from that daemon's parse.y. These are drop-in replacements: their parsers accept and reject exactly what parse.y does (byte-identity for ntpd, unwind-identity elsewhere).

RFC corpus (corpus/rfc/). The BNF fragments of the RFCs, pulled in whole where they compile and in pieces where they do not. Each fragment keeps:

  • the RFC's ABNF verbatim — <rfc>-<n>.bnf, with the form hbnf compiles beside it as <rfc>-<n>.hbnf, its .md, and .vectors/;
  • the error messages hbnf gives and what each means;
  • the fixed-up version, or — where the repair is involved — a note saying how to make it (e.g. a <prose-val> that defers its real definition to two or three other RFCs is rewritten to the rules those RFCs give, with the provenance named).

The corpus is where discoverability is proven: a fragment is "done" when its messages alone tell the author how to fix what hbnf could not accept silently.

**ALGOL 68, and C++ after it: far in the future (the user, 2026-10-22: "defer c++ and algol68 to far in the future"); on 2026-10-31 they went on the todo list, with COBOL, as step 20.** They were next in the running order (the user, 2026-10-18: "do algol68 before c++"), and nothing else waits on them now. ALGOL 68 is to be written in an hbnf that has gained what the W-grammar does (the user, 2026-10-18: "we won't do ALGOL 68 in precisely the W-grammar, we'll do it in the hbnf that is updated to do what a W-grammar does"): parameterised rules for the Report's NOTION families (built 2026-10-19: list(X), number parameters over a domain, clauses for single values, domain and growth checks, every backend; tests/params.sh), a back-reference for consistent substitution, where as the context and %where machinery of decision 13, and a checking pass over the AST for modes and coercion. METACOMPILERS.md ("W-grammars") says what each is. ALGOL 60 first (done 2026-10-18: corpus/algol60/algol60.hbnf, tests/algol60.sh). What ALGOL 60 taught, to carry into the W-grammar work: a "not followed by" test and trying the next alternative after a later failure (decision 14) would let the Report's BNF be used as it is written (its arithmetic/Boolean split, its : and :=) instead of rearranged; and two generator bugs on recursive grammars were found and fixed. **The test is built (2026-10-18, C): !x and &x**, so the grammar says label ":" !"=" and the assignment no longer has to be tried first; x is a literal, a rule (a token, or since 2026-10-31 a phrase, parsed where it stands and given back) or alternatives of those (!( "=" / ":" )), is read like any element after the blanks, and leaves no trace if it fails (it runs on a copy of the parser); tests/lookahead.sh. Still to come: the retry after a later failure, then parameterised rules.

Decisions

  1. Two alternation operators, two meanings.
    • | is ordered choice, as in PEG and as parse.y grammars are read: the first alternative that matches wins. The shadowed-alternative check stays.

    • / is ABNF's union: every alternative is legal. Between character ranges it is a set, the same as |; in a character rule the scanner takes the longest alternative. Between phrases it compiles without backtracking, and the author writes it as the RFC does:

      • the reader looks for an order of the alternatives in which ordered choice accepts the same language — no alternative can match text that a later one matches more of, or (when it matches the same text and what follows the choice could continue it) less of — and writes the choice in that order. "Longest first" is found, not required of the author; the one that can match nothing goes last;
      • this is decided on the alternatives' text, with an automaton per alternative searched for the shared text, so there is no limit on how many code points it takes to tell two alternatives apart (1*DIGIT "." / 1*DIGIT ":", "a" "b" "c" / "a" "b" "d");
      • what no order fixes is a union that needs backtracking: two alternatives that match the same text with different continuations (IPv4address / reg-name). hbnf takes the first alternative that matches and is followed by something that can follow the choice, as RFC 3986 section 3.2.2 says for host ("first match wins"), with a warning naming the two; a %where { } block (decision 13) is the author-written form of the same check.

      (Amended 2026-10-06, step 5. The plan was FIRST/FOLLOW sets and factoring a shared prefix, p = "a" / "a" "b" into p = "a" [ "b" ]. A first cut with two code points of lookahead resolved the RFC corpus's / except where the difference came later (h16 ":" h16 / IPv4address), and a fixed depth is a surprise. The automaton check needs no factoring, and keeps the tree types: reordering does not change them.)

  2. **Incremental alternatives are =/, ABNF's spelling, and nothing else.** No BNF dialect we know has =| or |=. (yacc gets the same effect by allowing name : more than once.) =/ extends the current definition; an =/ with no = before it is an error. The new alternatives join with /, so =/ is union, and compiles where / does.
  3. A later = overrides. It replaces the earlier definition, in the same file or another; the rule keeps its place, so an overridden root is still the root. (As built: in one file, or between two included files, the rule keeps its place; a file's own rules come before what it includes, in the order it writes them, since that order is the scanner actions' order. The root is the top file's first new rule, or, when it has none, the root of what it includes.)
  4. Include once. A file is read the first time it is included; later includes of it (by any path to the same file) do nothing.
  5. Directives come in two kinds.
    • Per file: those that change how the text of their own file is read. They apply only to that file; an including or included file is not affected. language (the language of the file's code blocks) today; sensitivity and whitespace (below) when they land.
    • Whole parser: those that describe the one generated parser: statements, macros, includes, keywords, conf, entry, prefix, layout_ops, wordchars. Any file may set one (layout tailq sets layout_ops for all nine daemons); two files that set one differently are an error. keywords lists from several files merge. Code blocks (the { … } preamble and epilogue) are joined in include order.

  6. sensitivity, per file, two independent axes:

    sensitivity %i ; rule names and literals sensitivity rule-name %i ; digit finds DIGIT sensitivity string %i ; "HTTP" matches http

    The default is %s on both, today's behaviour. A literal's own %i or %s always wins. A folded rule name keeps the spelling of its definition in generated identifiers; a reference that folds to two different rules is an error.

  7. One parsing model: characters, not a hidden lexer. Today a generated parser cuts its input into words, numbers, quoted strings and punctuation first, skipping blanks, and the rules match those tokens. So "x" "y" accepts x y and rejects xy, the opposite of ABNF, and 1*VCHAR fails on /x because x was already made a word. The generated parser will instead read characters: a literal compares bytes at the current position, a character rule's scanner runs at the current position, and a scanner action is called there.
    • The old lexer becomes grammar in a shared include: word, number, quoted strings with escapes, # comments and backslash continuation, as character rules anyone can read and change. wordchars becomes a grammar rule.
    • whitespace ws, per file: phrase-level rules in that file skip the rule ws between their elements; character rules never do. Daemon grammars say whitespace ws with ws = SP | HTAB | comment; RFC grammars do not, and match SP, WSP and CRLF where they write them.
    • Keywords stay a table: a word listed there does not match word.
    • Speed: the current lexer is fast because it cuts tokens once and branches on keyword ids. The character model keeps that by remembering the last token scanned at a position and branching on the first byte. The §6 numbers (57 ms for the 100,000-rule toy, about 0.5 s for 100,000 pfctl rules) must not get worse.

  8. Scanners, actions and emitters are code — one family of three. A %scan{ }, %action{ } or %emit{ } block holds the code that runs, usually one call to a function the file defines in its epilogue (%scan{ return ipv6_match(s, pos, len); }), with the function's prototype in the preamble. hbnf never rewrites the code. Most of the remaining 17 scanner actions become character rules instead, which also makes them work in Rust, Zig and Ada.

    The family has one member per level, and the levels are the compiler's own:

    level runs
    %scan{ }lexical recognize characters at this position
    %action{ }semantic on this node, after the parse
    %emit{ }generative write output for this node

    %emit{ } is agreed as the third member (2026-10-03) and is what would let a backend be a schema rather than Ada — step 13b. It is not built, and the semantics the three share are not finished: a block should be able to sit between elements rather than only at the end of a rule (step 12), which also gives one block per alternative instead of one per rule, and a block may name a template as shorthand for the code that renders it. Those are changes to the family, not to one member, which is the test of whether a member belongs in it.

  9. <prose-val> reads as a rule nobody has written yet: generation stops with file:line:col, the source line with a caret under the <…>, and "not written yet:" and the text in the angle brackets. The author writes the rule or a scanner action. A hole left for later is then a schema error that points at itself, rather than an XXX in a comment.
  10. Core rules. common.hbnf includes ascii.hbnf and holds the RFC 5234 Appendix B.1 classes (DIGIT, ALPHA, …, WSP = SP | HTAB) and CRLF = CR LF; ascii.hbnf holds the named single characters (the C0 controls, blanks, DEL, DQUOTE). LWSP waits for repetition inside character rules, which Is_Char_Rule refuses today.
  11. Negation is ~. Done 2026-10-17 (tests/schema.sh, in all four backends). ~rule matches one code point not in the set rule matches (a complement); repetition composes, so *~rule is "until rule" (SNOBOL's BREAK). A hbnf extension — ABNF has no negation — and it collapses the explicit %x complements the lexer rules would otherwise spell out: comment = "#" *~LF, string = DQUOTE *( "\\" %x00-10FFFF | ~(DQUOTE | "\\") ) DQUOTE.
  12. Comma lists are #. Built 2026-10-18 (tests/commalist.sh). # is * with an implicit comma separator: n#m element is comma-separated repetition, #element is 1#element. It is sugar for element *("," element) — the same list the daemon grammars write left-recursive — so it inherits parse.y's semantics: no trailing comma, no empty elements. Deliberately stricter than HTTP's #rule, which allows empty elements (a known server-bug source).

  13. Context-sensitivity: a %where { } block. C is the standing example: with typedef int A; in scope, (A) * 0 is a cast of *0, and with int B; in scope (B) * 0 is a multiplication. The two cannot be told apart without consulting a symbol table during the parse, so no context-free grammar settles it. So does a name that parses and still has to be looked up (host as a DNS name).

    The bar here is lower than it looks, because tree-sitter does not solve this either. Measured 2026-10-01 against tree-sitter-c: both lines produce the same tree, `(binary_expression (parenthesized_expression (identifier)) (number_literal))`. The typedef case is simply wrong — it has a cast_expression rule and cannot tell when to use it, so precedence picks multiplication both times. That is fine for highlighting and is not a correct parse. So "as general as tree-sitter" does not require this; being right does.

    The shape is a block after an alternative, like %action{}, that decides whether the alternative holds:

    typedef-name = word %where { return is_typedef(text, len); } host = IP-literal / IPv4address / reg-name %where { return in_dns(text, len); }

    It is code, and hbnf does not restrict what the code does: it reads state, writes it, calls out to the network. What hbnf owes the author is the order it runs in, stated plainly: a %where runs each time its alternative is tried and has matched, in parse order, and an alternative that fails it (or a later element) is backed out of, so the block runs again where the parse backtracks and the same alternative is tried again. %scan{} is called the same way, at each position its rule is tried. %action{} is the one that runs once, after the parse, bottom-up, because the tree it reads is only complete then. Like the scanners, a %where is written per backend (%where Rust { }), and the guard hbnf writes itself for a union that needs backtracking (first match wins, see decision 1) is the same hook with generated code.

    It does not make hbnf ambiguous: the block decides a branch, it does not explore several.

    **Settled direction (2026-10-17, the user's): context is data the grammar names, scoped, and the parser threads.** hbnf was never context-free -- ordered choice, scanner actions, exceptions and the wire layer's expressions over earlier fields are already outside it -- and "context-free" described only what BNF alone can decide. Context is stored by the grammar and consulted by the parser, in a notation a BNF reader is not surprised by:

    context types ; a scoped set of names typedef-name = identifier ? types ; an identifier that is in types declaration = specs declarators ";" %bind types += declarators.name block = "{" %scope *statement "}" ; bindings made inside vanish at "}"

    • A context is a persistent value. %bind makes a new version and a backtrack restores the old one, so a speculative bind costs nothing and leaks nothing, and a bind may run during the parse, where a later ? test sees it. (This is the answer to why %action waited for the end of the parse: side effects a backtrack cannot undo. A persistent value has none to undo. %action stays the post-parse member.)
    • A definition is a label (the user, 2026-10-18: "foo: mv r0,r1 is like foo := lambda mv r0,r1"). A label, a procedure, a typedef and a macro are one thing: a name bound to what follows it. So the context is not only a set of names: an entry may carry a value (the node, or the place in the text), a use looks the name up, and a use before the definition (a forward GOTO) is a lookup that the AST walker does after the parse, where every definition is known. Not built: a value stored with a name.
    • Code for what the notation cannot say: %bind { } and %where { } in any language, reading and writing the context through a small API.
    • Precedents weighed: Prolog DCG arguments and attribute grammars (inherited attributes: pure, but heavy to write), yacc's lexer hack (a mutable global; unsafe under backtracking), ANTLR's semantic predicates (the author owns the hazard), IMP72's syntax extension (powerful, a much bigger machine).
    • Where it lands: step 6, with the other compiler-compiler interfaces, in C first, tested on (A) * 0 (a cast when A is a typedef name, a product when it is not) before a C subset is tried.

    **Built 2026-10-18 (C), in the first spelling, local to the rule that uses it** (the user: "keep things local ... but clean and easy to read"): context types templates declares contexts; identifier ? types fails the alternative unless the text just matched is in types; `%bind types += declarators.name` adds a field's text when that point of the rule is reached (or %bind { code }); %scope makes what is bound after it vanish when the rule's alternative ends; %where { code } is a test with the matched text as text, len. Code reads and writes a context with HBNF_IN (ctx, s, n) and HBNF_ADD (ctx, s, n). A context is a stack of names with a hash index, so a lookup is a hash and putting it back to a mark is a pop; every branch of an alternation, every iteration of a repetition and every rule that can fail takes a mark and returns to it when it gives up, so what a wrong guess bound is gone with the guess. Only a grammar that declares a context pays for any of it. tests/context.sh runs the six cases (cast, product, undeclared, inside a block, after the block, a guess that bound and gave up). C only; the other backends refuse context with a message. %where and %bind { } are in the file's language (C). Not yet: negation (? !types), a value stored with a name, contexts across the statements of a statements parser.

  14. Ambiguity: fork only where it occurs, and settle it in a fixed order. (Decided 2026-10-18, from the study of hbnf15.txt, with the user.) Ordered choice stays the fast path: a choice the generator can show is decidable costs what it costs today. The generator looks for the choices it cannot show are decidable -- alternatives that can match the same prefix and are not told apart by a fixed lookahead, conservatively, since ambiguity of a context-free grammar is undecidable and a false positive costs only a fork -- and gives only those a local fork: both readings are kept for the span of the ambiguity, then one is chosen. Nothing is annotated by the author, and the points are reported when the parser is generated (to stderr, with the rule, the alternatives and the reason; --quiet-forks silences it). The choice is made in this order:

    1. a %where or a context test (?) that fails removes its reading;
    2. IMP72's first rule: a terminal over an expression -- a word that appears literally in a pattern beats the same word read as a variable (keywords over identifiers, contextual keywords such as final);
    3. IMP72's second rule: the reading that uses the fewest distinct rules;
    4. where IMP72 picks arbitrarily, hbnf takes **the first alternative in the order the grammar wrote them** -- the same first-match rule as the rest of the notation, so a fork never introduces a new kind of behaviour.

    The memo of a rule's result at a position must be keyed by the context's version, or skipped for a rule that reads context, or a cached typedef decision would leak across scopes. This replaces "GLR, or trying another alternative after a later failure" under Not in this plan. Built, in its local form (2026-10-18, C, --forks; tests/forks.sh): the generator lists the rules whose alternatives can start alike (leading literals, a prefix counts, a token meets a word), and a call of such a rule that is followed by more of its sequence is wrapped in a retry: when the rest fails, the fields from there on are freed, the position and the context mark restored, and the rule is entered again at its next alternative. The tie-break order above is not built: the first alternative that lets the sequence finish wins, which is IMP72's third rule alone. Not built either: a retry across a rule's end (the caller of the caller), forks with %where or ? after the fork, and the other backends.

POSIX BNF

Step 7's copy-paste goal is for RFC ABNF. POSIX's own grammars are a second notation worth the same treatment: the yacc BNF POSIX writes its standard utilities in — name : rhs, ;-terminated, %token declarations, /* … */ comments, and left recursion for every list. The test case is the Shell Command Language grammar (POSIX.1 §2.10, the Bourne shell): the largest such grammar, and the one that leans hardest on yacc's tokenizer feedback, so it exercises every difference at once. It becomes a third corpus once the reader work below lands.

The bar is the RFC one: a pasted spec is corrected by the messages, not by reading the manual. POSIX BNF needs one change to the pasted text — give each %token name a definition — and one rewrite where yacc steers its lexer from the parser and hbnf's character model makes the steering unnecessary. Both are kinds hbnf already knows how to point at.

Ordering and token tables

Researched 2026-10-02, because the question deserves an answer and not a restatement of decision 7: *why did we go against token tables, shouldn't foo = "bar" go into one, and why is %token needed at all?*

Three answers, and the first thing to separate is the two different things "token table" can mean. A keyword table interns the fixed literals a grammar names and gives each an id. A token array cuts the whole input into tokens before any rule runs. hbnf kept the first and dropped the second, and the confusion between them is doing real damage to this plan.

1. foo = "bar" already goes into a token table. Is_Keyword_Lit in the C backend: a literal led by a letter or _ is a keyword, and when a grammar has no keywords { } table every such literal is one. So "bar" is already interned, already in the generated kwid_t enum, and already looked up by kw_lookup. The user's instinct is the implementation; nothing needs adding.

The keywords { } directive only ever narrows that default, and it exists for exactly one reason: parse.y's lookup() reserves a word everywhere in the file, so a word in the table does not match STRING anywhere. Byte-identity with parse.y therefore requires hbnf to reserve the same set, no more and no less — which a default of "every letter-led literal" does not give, because the daemon grammars name literals parse.y does not reserve. The POSIX shell grammar shows the other edge of the same tool: if is reserved only in command position, so a table that reserves everywhere is the wrong instrument there and the rules must spell if as an alternative instead.

**2. What was dropped was the token array, and the reason was correctness, not speed.** Decision 7 has it: the pre-cut array imposed a tokenization the grammar never asked for. "x" "y" accepted x y and rejected xy — the exact opposite of ABNF, where concatenation is adjacency — and 1*VCHAR failed on /x, because the lexer had already decided x was a word. For RFC 5234 that is not a performance trade, it is the wrong language. The array also put the lexer outside the notation: wordchars was a directive, so a grammar could not say what a word is. Now it is a rule (wordchars = ALPHA | DIGIT | "_" | "-" | ".") that any grammar overrides, which is what let pfctl add $, @ and % and ntpd not.

So "we went against ordering and token tables" is not what happened. The keyword table is still there. What the array also carried, and what genuinely went with it, is the subject of the third answer.

**3. The id dispatch is what we lost, and it is recoverable without the array.** Measured in the generated pfctl parser: expect_kind — the token-era jump that read a token's interned id and branched on it — appears 72 times before 4c and zero times after. kw_lookup survives at three sites, all of them negative ("this word is reserved, so it is not a word"). Nothing dispatches on an id any more. A wide alternation instead calls expect_word per branch, which re-scans the word and memcmps it, and cc89c9e recovered part of the loss by switching on the first byte — which separates 7 of pfctl's 35 filteropt branches, because the rest share a leading letter.

That is most of the 1.61x instruction-count gap (190.3M against 306.6M at 5,000 rules): 73 scan_word calls and 191 skip_ws calls per rule, for a rule holding 14 words. Decision 7 predicted exactly this and promised two remedies — "remembering the last token scanned at a position and branching on the first byte." The first byte landed; the remembering did not.

**So the benefit the question asks about is real, and here is the shape it takes.** Not a token array: a position-keyed scan, which is the same economy without the wrong language.

  • Scan once per position (4c's deferred memoization). Prototyped 2026-10-02 in the generated C: a (position -> scan length) table for the word scanner with a generation stamp, 306.6M -> 258.7M instructions and 1.28x -> 1.12x against the token array. This is "remembering the last token scanned at a position", and it is the half of decision 7 still owed.
  • Dispatch on the id, not the first byte. Scan the word once at the branch position, kw_lookup it, and switch on the kwid_t — the token-era expect_kind jump, restored over characters. Correctness condition: a case for keyword K may jump to branch N only if no branch before N can begin with K, which is a FIRST-set computation hbnf already needs for its FIRST/FOLLOW-disjoint compilation. Branches led by a rule rather than a literal stay in the linear chain.
  • Measure it on an input that exercises it. A hand-built kwid dispatch over filteropt measured 307.1M, very slightly worse — because bench/gen.sh emits one rule shape whose only filter option is keep state, and keep is one of the 7 that first-byte dispatch already separates. The gate is being held against an input narrower than the thing it measures. gen.sh needs a mode that cycles the filter options before any of this is worth doing.

4. %token is not needed at all, and hbnf should never require it. In yacc, %token NAME declares a terminal whose spelling lives in the lexer, in C, outside the grammar; the declaration is the only thing tying the parser to a symbol it cannot see. hbnf has no outside lexer — the lexer is grammar — so a %token carries no information: either the name has a definition in the file, and the declaration is redundant, or it has none, and the grammar is simply incomplete. %token is therefore a **paste artifact and nothing more**: the reader accepts it so a POSIX or yacc grammar pastes unchanged, registers the name as declared-but-undefined so the error can name it by kind (operator, reserved word, lexical class), and requires it from nobody. A grammar written in HyperBNF never writes one. That is what the POSIX BNF section above specifies, and the reasoning is this.

Compiler-compiler completion criteria

The end state is deliberately broader than "an ABNF parser generator": one human-readable grammar describes syntax, lexical boundaries, wire representation and semantic construction, so the author never maintains a separate lex spec, yacc semantic-value protocol, AST schema and serializer. %scan{} and %action{} stay the escape hatches for target-language code; the remaining work adds the interfaces around them — not yacc's global state (yylval, yyparse, $1/$$), LR tables, or GLR.

A grammar is compiler-compiler ready when:

Ordering and token tables

Researched 2026-10-02, because the question deserves an answer and not a restatement of decision 7: *why did we go against token tables, shouldn't foo = "bar" go into one, and why is %token needed at all?*

Three answers, and the first thing to separate is the two different things "token table" can mean. A keyword table interns the fixed literals a grammar names and gives each an id. A token array cuts the whole input into tokens before any rule runs. hbnf kept the first and dropped the second, and the confusion between them is doing real damage to this plan.

1. foo = "bar" already goes into a token table. Is_Keyword_Lit in the C backend: a literal led by a letter or _ is a keyword, and when a grammar has no keywords { } table every such literal is one. So "bar" is already interned, already in the generated kwid_t enum, and already looked up by kw_lookup. The user's instinct is the implementation; nothing needs adding.

The keywords { } directive only ever narrows that default, and it exists for exactly one reason: parse.y's lookup() reserves a word everywhere in the file, so a word in the table does not match STRING anywhere. Byte-identity with parse.y therefore requires hbnf to reserve the same set, no more and no less — which a default of "every letter-led literal" does not give, because the daemon grammars name literals parse.y does not reserve. The POSIX shell grammar shows the other edge of the same tool: if is reserved only in command position, so a table that reserves everywhere is the wrong instrument there and the rules must spell if as an alternative instead.

**2. What was dropped was the token array, and the reason was correctness, not speed.** Decision 7 has it: the pre-cut array imposed a tokenization the grammar never asked for. "x" "y" accepted x y and rejected xy — the exact opposite of ABNF, where concatenation is adjacency — and 1*VCHAR failed on /x, because the lexer had already decided x was a word. For RFC 5234 that is not a performance trade, it is the wrong language. The array also put the lexer outside the notation: wordchars was a directive, so a grammar could not say what a word is. Now it is a rule (wordchars = ALPHA | DIGIT | "_" | "-" | ".") that any grammar overrides, which is what let pfctl add $, @ and % and ntpd not.

So "we went against ordering and token tables" is not what happened. The keyword table is still there. What the array also carried, and what genuinely went with it, is the subject of the third answer.

**3. The id dispatch is what we lost, and it is recoverable without the array.** Measured in the generated pfctl parser: expect_kind — the token-era jump that read a token's interned id and branched on it — appears 72 times before 4c and zero times after. kw_lookup survives at three sites, all of them negative ("this word is reserved, so it is not a word"). Nothing dispatches on an id any more. A wide alternation instead calls expect_word per branch, which re-scans the word and memcmps it, and cc89c9e recovered part of the loss by switching on the first byte — which separates 7 of pfctl's 35 filteropt branches, because the rest share a leading letter.

That is most of the 1.61x instruction-count gap (190.3M against 306.6M at 5,000 rules): 73 scan_word calls and 191 skip_ws calls per rule, for a rule holding 14 words. Decision 7 predicted exactly this and promised two remedies — "remembering the last token scanned at a position and branching on the first byte." The first byte landed; the remembering did not.

**So the benefit the question asks about is real, and here is the shape it takes.** Not a token array: a position-keyed scan, which is the same economy without the wrong language.

  • Scan once per position (4c's deferred memoization). Prototyped 2026-10-02 in the generated C: a (position -> scan length) table for the word scanner with a generation stamp, 306.6M -> 258.7M instructions and 1.28x -> 1.12x against the token array. This is "remembering the last token scanned at a position", and it is the half of decision 7 still owed.
  • Dispatch on the id, not the first byte. Scan the word once at the branch position, kw_lookup it, and switch on the kwid_t — the token-era expect_kind jump, restored over characters. Correctness condition: a case for keyword K may jump to branch N only if no branch before N can begin with K, which is a FIRST-set computation hbnf already needs for its FIRST/FOLLOW-disjoint compilation. Branches led by a rule rather than a literal stay in the linear chain.
  • Measure it on an input that exercises it. A hand-built kwid dispatch over filteropt measured 307.1M, very slightly worse — because bench/gen.sh emits one rule shape whose only filter option is keep state, and keep is one of the 7 that first-byte dispatch already separates. The gate is being held against an input narrower than the thing it measures. gen.sh needs a mode that cycles the filter options before any of this is worth doing.

4. %token is not needed at all, and hbnf should never require it. In yacc, %token NAME declares a terminal whose spelling lives in the lexer, in C, outside the grammar; the declaration is the only thing tying the parser to a symbol it cannot see. hbnf has no outside lexer — the lexer is grammar — so a %token carries no information: either the name has a definition in the file, and the declaration is redundant, or it has none, and the grammar is simply incomplete. %token is therefore a **paste artifact and nothing more**: the reader accepts it so a POSIX or yacc grammar pastes unchanged, registers the name as declared-but-undefined so the error can name it by kind (operator, reserved word, lexical class), and requires it from nobody. A grammar written in HyperBNF never writes one. That is what the POSIX BNF section above specifies, and the reasoning is this.

Order

Each step leaves the nine daemon grammars, e2e, byteident (ntpd) and unwind-ident passing; each lands as reviewed patches.

**A switchover step's gate must name the old mechanism and assert it is gone.** Two switchovers in this plan were marked done while half-finished, and both times the gate was structurally unable to see it. Step 3's gate was "byte-identical output for every schema through every backend" — which a flat ${name} substituter passes exactly as well as Mustache does, so a renderer could be written, wired to nothing, and the step still close. Step 4's gate was the daemon grammars, byteident and the corpus, all of which run through the backends — so the interpreter could stay on tokens and every gate still pass. Testing the output cannot test the mechanism. A switchover therefore gates on a count: zero Templates.Render callers and zero ${ in the templates (3b), zero Token_Vectors outside the reader's own lexer (9c). Those are the assertions that fail loudly while the old path is still there.

**Correct first, optimize after — and a regression that buys correctness is expected, not a defect.** Every step still ahead adds accuracy or adds a feature: characters where there were tokens, a pointer where a type was refused, a warning channel, spans, recovery, a wire layer. Each of those costs cycles, and the cost is predictable — a parser that checks more does more work. So a performance number that moves the wrong way after a correctness step is recorded and left alone; it is not a reason to stop, to revert, or to interleave optimization into the step that caused it. Optimization happens once the feature set is settled, against a measurement taken then, and 4f sits at the end of the running order for that reason.

What does not relax is the honesty rule: **paper claims match measurements.** A step that moves a number re-measures and updates §6 rather than leaving the old figure standing. Recording a regression is cheap; a stale claim is the thing this project does not ship.

    Designed, not built (the user, 2026-10-17):

    **Direction (the user, 2026-10-17): text and binary are freely mixable; there is no binary mode.** What was built first was a separate path -- hbnf_wire.adb had its own lexer and parser, a binary line picked it, and a file was all bit rules -- a shortcut, not the design (stage 1 below removed it, 2026-10-17). The design is one notation, one reader, one emitter per backend:

    1. One reader. The bit forms (name:N, name@K:N, 0x and 0b constants, [expr], ?( ), *u8, %action/%emit) are elements of the main notation; language is a directive of the main reader. The wire emitters stay, fed by lowering the unified rules. (units, a directive that spelled a message as words, was a stopgap and is gone: 2026-10-18, replaced by name:bitsof(rule), below.)
    2. Rules refer across the boundary (a text rule holding a bit rule and the reverse), through one parse state.
    3. Interleaving inside a sequence -- `"GET " len:16 payload:[len] "\r\n"`: the input position is an octet and a bit offset; text elements run when the offset is 0 (and say so when it is not), bit elements run anywhere. This changes the four text backends, and the wire emitters fold into them.

    Everything is bits, octets are runs of bits, text is octets read as UTF-8. Layers, not octets (the user, 2026-10-17). Because each layer is a run of units of the one below, the unit of the middle layer is not fixed at 8 bits: a machine with 9-bit bytes or 18-bit words is the same grammar with another width (byte 9, word 18). A char is a code point; its UTF-8 form is a string of octets that maps to it. And one slice syntax serves every layer: foo:4 is 4 units and foo@1:4 is 4 units at offset 1, the unit being the layer of foo (bits for a bit field, octets for an octet run, chars for a string). The notation was weighed against COBOL's foo(2:4), BLISS's foo<p,s>, Ada's foo(2..5) and Python's foo[1:5]; @offset:length is the nearest to COBOL's and PL/I's offset-and-length and to Ada's at, and stays.

    **The user's formulation, 2026-10-17: octets are tokens over bit arrays, and strings are tokens over octets.** A token is a run of units of the layer below (decision 7: a rule with no named children is a token, scanned by a table), and the lowest alphabet is the bit. ABNF already has BIT and OCTET among its core rules, so ttl = 8BIT is a bit field and name:8 is a convenient spelling of it. Three consequences: a token over units of width W may start at any bit (an octet is eight bits from wherever you are, so text after a 5-bit field is read shifted -- an alignment rule was added in stage 2 by mistake and removed 2026-10-18); the DFA scanner and the union analysis carry over to a bit alphabet, so a value set (0x0800 | 0x0806) is a token over bits; and a token's value type follows its alphabet (a number for bits, a byte string for octets, a string for code points).

    Character sets (the user, 2026-10-18; decisions still to be taken). The middle layer's width is a file parameter (byte 6, byte 9, word 18: "take the stream N bits at a time"), and the layer above it is chars, so what a unit means as a char is a mapping the file must name: ASCII, Latin-1 and the other ISO 8859 and Windows code pages, EBCDIC (IBM's 037, 500, 1047 and others), DEC SIXBIT, CDC display code, FIELDATA, 9-bit ASCII on the 36-bit machines. A char is still a code point; a character set is a table from unit values to code points (many are partial, with holes), and a token over it is scanned the way a token over octets is. Taste decisions to take before building:

    1. Where the name goes. A directive for the file (charset EBCDIC-1047), a per-rule or per-field override for mixed files (an EBCDIC header over an ASCII payload), or both.
    2. Literals. "GET " is code points; in an EBCDIC file it must become the units that spell them, at generation time, so a literal is written once and means the same thing in every set. %d13.10 and %x constants stay unit values, not code points.
    3. Core rules. ALPHA, DIGIT, SP and CRLF are defined over code points, so they follow the file's set; OCTET and BIT do not.
    4. Standard tables, not our own. The tables exist (IBM's CDRA, the unicode.org mappings, glibc's iconv/gconv tables, ICU's ucm files), so, as with checksums, hbnf takes them by their own names and attributes them instead of retyping them; whether the generated parser links iconv or embeds a table is the open point (a self-contained parser argues for a table, generated from the standard mapping file, per set actually used).
    5. Holes and errors. A unit with no code point is a parse error that says which unit and which set; whether a set may declare a replacement is for later.

    Answers (the user, 2026-10-18), and what follows from them:

    1. Both. charset NAME for the file, and a per-literal prefix (like C's u8"..." and L"...") or per-rule override for mixed files.
    2. Literals: options. (a) Literals are code points and are transcoded to the file's set at generation time, so "GET " in an EBCDIC 1047 file is the units C7 C5 E3 40; a character the set lacks is a generation-time error naming the character and the set. (b) Literals are unit values: only %xC7.C5.E3.40 is allowed outside Unicode files; explicit, no magic, but an RFC's ABNF cannot be pasted in. (c) A prefix names the set per literal: ebcdic"GET "; exact and good for mixed files, verbose for whole ones. Recommended: (a) as the default with (c) as the override, so a file says its set once and a literal says otherwise only when it differs.
    3. Core rules, fleshed out. RFC 5234 Appendix B defines ALPHA, DIGIT, SP, CRLF, VCHAR and the rest by numeric values of US-ASCII, which are Unicode code points below 128. So the rule is: %x41 and the core rules name characters (code points), and are transcoded exactly as literals are; in an EBCDIC file ALPHA is the units for A-Z and a-z (C1-C9 D1-D9 E2-E9 81-89 91-99 A2-A9), not the values 41-5A. The raw-unit spelling is the bit-field constant, 0xC1, which already means a value of that many bits, not a character. So %x is the character form and 0x the unit form, with no new syntax. OCTET and BIT are layer names, not characters, and do not change (OCTET is a unit of the middle layer, 9 bits in a byte 9 file); non-ASCII characters in a core-rule position are written as literals or %x code points, as now.
    4. Link nothing unless it is needed. ASCII and UTF-8 need no table and no library. A one-unit set (at most 9 bits, so 512 entries) is a table generated at hbnf time from the standard mapping file (the unicode.org mappings, glibc's charmaps; attributed, not retyped) and embedded in the parser. Only a multi-unit set (Shift-JIS, GBK) links iconv, and only a grammar that names one pays for it.
    5. Unassigned units are not a decision: a unit with no character in the set read as text fails with a message naming the unit, the set and the position (`unit 0x41 at 17 is not a character of EBCDIC-1047). Read as bits or octets (0x41, name:8`), it is just a value, so a binary field inside an EBCDIC file is no problem.

    6. Round trip is always possible (the user's requirement). The approach: what was read is kept. A token's value is its code points, and the units it came from stay reachable (they are a slice of the input, as strings already are). Writing a tree that was parsed and not changed re-emits those units exactly, whatever the set's mapping. Writing new text encodes each code point by the set's inverse; where the mapping is not one-to-one the table says which unit is canonical (the lowest, unless the standard names one). The examples that make this necessary:

      • Two units, one character (illustrative: a vendor table that maps two control units to the same code point): reading is fine; an unchanged token writes back its own unit, a new one writes the canonical unit.
      • Overlong UTF-8 (C0 80 and 00 both mean U+0000): the standard forbids it, so the reader refuses it with a message rather than keep two spellings of one thing.
      • A character the output set lacks (U+00E9 into SIXBIT, or into EBCDIC 037 variants without it): not recoverable, since no unit spells it; the writer fails with a message naming the character, the token, and the set. That is a property of the set, not a round-trip failure of anything that was read.

      So no parse is ever unwritable; only new content that the output set cannot spell is refused.

    7. UTF-8 maps to code points, transparently. It is the default set; a file that never says charset reads and writes UTF-8 with no table; and a char is a code point at the grammar level in every set.

**What the tree keeps today, and the gap.**  The tree is a struct of the
named children (the union of all alternatives' members), a string for a
token, a list node for a repetition.  It does not keep the literals (they
are in the grammar), the blanks, whether an alternative was taken when its
members are the same as another's (`a = b "x" / b "y"`), or which optional
part was present when it has no member of its own.  Only a leading literal
tags an alternative (`Leading_Tags`).  So a writer cannot recover every
tree; the parser must keep what the grammar does not say.
**Design.**
1. *An opt-in `writer` directive (or `--writer`)* makes the generated
   parser record, for each alternation, the number of the alternative
   taken (`_alt`), and for each optional part, whether it was present
   (`_has_N`) -- only where the tree does not already say.  Without it the
   parser, the tree and every byte of generated output are unchanged (the
   byte-identity gate stays).
2. *A generated `write_<rule>`* per rule, walking the tree by the same
   `Rule_Info` the walkers and free functions use (`Emit_Walk`,
   `Emit_Free`): a literal is written from the grammar, a token from its
   text, a repetition node by node with its separator, an alternation by
   its recorded number.  Blanks: `ws` is not remembered, so between two
   items the writer puts one space where the grammar has a `whitespace`
   rule and the previous character and the next would otherwise run
   together, and nothing where `whitespace none`.
3. *The check is the gate, built in:* `write_checked` re-parses its own
   output and compares, so a grammar whose canonical text is not what it
   reads (a token that glues to the next, a blank that matters) says so
   in the test and, at run time, refuses.
4. *Mixed grammars:* a text rule that holds a bit rule calls
   `emit_bits_<rule>` (built), and the octets are written as bytes; a
   bit rule that holds a text rule calls `write_<rule>` at whatever
   bit it is, the octets written shifted.  Numbered-word text (BIP-39, bech32) writes through the same
   path: a token's value is its spelling, so `bitsof` (built) needs only the
   spelling of each number.
5. *Order of work:* `_alt`/`_has` recording and `write_` for sequences,
   literals, tokens, lists and optional parts; alternations; left-recursive
   lists (`sum = sum "+" n`); then `--writer` on obconf (it has a printer
   to compare with), then the suites' round trip, then mixed grammars.

    • A cost model, not a panic rule. Recovery is a scored search — tree-sitter prices a skipped or inserted token and keeps the cheapest repair — rather than "discard to the next newline".

  1. A tree-sitter emitter, as an editor backend. Not a replacement for

the C backend and not gated on anything above: it can land between any two other steps. The idea is to generate a grammar.js (and a stub scanner.c where a scanner action is needed) from the lifted schema, so one grammar gives both the daemon's parser and the editor's highlighting, folding and structural selection. Today a daemon ships a parse.y and, separately, somebody hand-writes a tree-sitter grammar that drifts from it; one source removes the drift.

The mapping is mostly mechanical, because tree-sitter's grammar.js is the same shapes under different names:

| hbnf | grammar.js |

|---|---|

| a rule | an entry in rules |

| concatenation | seq(...) |

| \| | choice(...) — see the catch below |

| [ x ] | optional(x) |

| *( x ) / 1*( x ) | repeat(x) / repeat1(x) |

| a character rule | token(seq(...)) |

| a lifted rule_1 | an inline: rule, so the CST keeps the written shape |

| whitespace ws | extras: |

| the keyword table | word: |

What does not map, stated plainly rather than papered over. This list is the reason the emitter is a separate backend and not a mode of the others:

  • choice is not |. hbnf's | is PEG ordered choice: the first branch that matches wins, and that is what makes a parse deterministic without annotations. tree-sitter is GLR; choice is unordered, and an ambiguity it cannot resolve is a build error demanding hand-written prec() or conflicts. So a schema hbnf compiles can fail to build as a tree-sitter grammar, and the emitter must say so rather than guess a precedence. / (ABNF union) maps better than | does.
  • n*m bounds. tree-sitter has repeat and repeat1 and nothing else; 3*5( x ) has to be unrolled, and the unrolling shows up in the CST.
  • Scanner actions become externals: plus a scanner.c. The emitter can stub the scanner with the scanner action's own code where the scanner action is already C, and must otherwise leave a named hole.
  • <prose-val> has no analogue: an unwritten rule cannot highlight. It emits as an externals: hole with the prose as its comment.
  • sensitivity/%i has no analogue either; a case-insensitive literal becomes a regex, which changes the token boundaries.
  • Typed fields, actions and bindings are out of scope. An editor backend produces a CST of named nodes; it does not produce the daemon's structs, and nothing in it is byte-identity tested against a parse.y.

Gate: the nine obconf grammars build as tree-sitter grammars, the obconf sample configs highlight, and every CST node name is the rule name that produced it. Where a grammar cannot build without a hand-written precedence, the emitter names the rule and the conflicting branches.

*Two claims in the original proposal are wrong, and the corrected numbers are why this is an editor backend rather than a parser strategy.* Measured 2026-10-01, same grammar, same input, gcc -O2, best of 5:

| input | hbnf | tree-sitter |

|---|---|---|

| 7.68 MB | 48.33 ms, 21 MB | 501.75 ms, 117 MB |

| 76.9 MB | 488.82 ms, 202 MB | 5158.51 ms, 1155 MB |

  • "A full parse of a config is in the same league as your RD parser" — it is 10x slower and takes 5.6x the memory (~159 MB/s against ~15 MB/s).
  • "Incremental reparse is the win" — for a config it mostly is not. A one-byte edit in the 7.68 MB file reparses in 87 ms, still worse than hbnf's 48 ms cold parse, because a config is a flat list of N siblings and an edit prunes nothing. For deeply nested source tree-sitter wins this outright; the conclusion is scoped to the input shape hbnf targets.

On the size estimate ("smaller than the Zig backend, a few hundred lines, call it a week"): the backends measure hbnf_rust.adb 1,952 lines, hbnf_zig.adb 2,167, hbnf_ada.adb 2,292, hbnf_c.adb 5,650. A few hundred lines is plausible for the grammar.js emitter alone — it writes no types, no free functions, no walkers and no parse functions — but the scanner stubs, the conflict reporting and the highlight fixtures are the rest of it.

On the number: the proposal filed this as "4b", which is taken (the lexer as grammar, done). It is 11 because it is not on the path to any gate above, not because it comes last.

13a. A grammar for the notation, and a round-trip pretty printer. The last step, because it is a claim that the notation is finished — which is also the sense in which this step freezes the notation. Its printer projects every construct onto four historical notations, so a construct added after it is written is a construct added in five places. Step 12 therefore carries the outstanding notation decisions, small as they are, and nothing should arrive here unsettled.

Not the file that already exists. hbnf_schema.hbnf is a grammar for hbnf the configuration format — config = *( entry ), blocks and statements, the pf.conf-shaped language — and is for the interpreter; all four backends refuse it today (undefined dec, comment). This step wants the other thing: a grammar for **the .hbnf schema notation itself**, so hbnf describes the language hbnf is written in. Different file, and the names must not be confused: call it hbnf.hbnf.

That makes hbnf self-describing, which is the thread HISTORY.md follows from McCarthy's eval onward — and the same caution applies. A self-description is trivial when the defining language is understood, so the thing that makes it worth more than a demonstration is the second half:

A round-trip pretty printer. Read a schema, print it, and get the same meaning back — with comments preserved, not discarded, because a grammar's comments are half of what it is for. The reader already keeps a leading and a trailing comment per rule and round-trips them into generated output, which is the foundation; this needs them kept through a full re-print.

There is prior art one layer down, and 9c did not throw it away: tests/hbnf_check.adb was a conformance driver whose "accept" required exactly this — parse, print, re-parse, re-print, and the printer must be idempotent — for the config format, against HBNF_Config's printer. 9c rebuilt that driver against generated code (tests/schema/print_main.adb, run by tests/schema.sh); this step is the same discipline applied to the notation. The old printer also kept comments, which the generated tree does not yet: that is this step's.

  • Normalizing by default. One rule per definition, spelled =: ::=, := and : all print as =. Comments print as ; to end of line: /* */ and (* *) are read and normalized away. The point is that a grammar pasted from anywhere comes out in one house style, and a diff between two schemas is about the grammar and not the notation.
  • --preserve keeps each definition's and each comment's own spelling as written, so a pasted RFC or POSIX grammar round-trips byte-for-byte. That is the stronger gate and the one worth testing: read, print, compare to the input.
  • Historical styles on request. Print a schema as ALGOL 60 BNF (::=, angle-bracketed names), as Wirth EBNF (:=, (* *), { } repetition, [ ] option), as yacc/POSIX BNF (:, ; terminators, /* */, %token declarations for the char rules), or as RFC 5234 ABNF (=, =/, / union, */n*m repetition, ; comments). Each is a projection of the one grammar onto one notation, and each is a test of the reader: whatever the printer emits in style X, the reader must read back to the same grammar.
  • Where it cannot be faithful it says so. Not every grammar projects onto every notation: ordered choice has no ABNF spelling, n*m has no yacc spelling, a scanner action has no spelling anywhere. The printer names the rule and the construct rather than emitting something that reads as equivalent and is not — the same rule step 11 holds for the tree-sitter emitter.

Gates. hbnf.hbnf reads every schema in the tree, including itself. --preserve round-trips all of them byte-for-byte. Normalized output of any schema generates parsers byte-identical to the original's (the snapshot, run on printed schemas). And every historical style reads back to the grammar it was printed from.

13b. Closing META II's loop: the classification in the notation. Open, and open to argument. Not scheduled; recorded because it is the one thing between 13a and a self-hosting hbnf, and because the shape it should take is a design question worth settling before anyone writes code.

What stands in the way. 13a makes hbnf self-describing, which is weaker than self-compiling — hbnf.hbnf through hbnf yields a parser for HyperBNF schemas, not hbnf. What is missing is the part that chooses how a rule is emitted: Analyze, Rule_Info, and the Scalar/Enum/Struct/List classification, which decide which template a rule shape gets. Those are Ada, and until they are expressible in the notation the loop does not close.

3b moved this much closer than it looks. The emitters are no longer Ada that writes C; they are 65 {{ }} templates driven by the tree, with the Ada reduced to choosing which template a rule shape gets. The output shape is already data. Only the choosing is not.

**The requirement, stated as a constraint and not a wish: it must not feel bolted on.** A per-rule shape declaration would be a bolt-on twice over — it adds notation, and it duplicates what the rule's pattern already says. Whatever this becomes has to read like the notation grew it.

The shape is decided: %emit{ }, the family's third member (agreed 2026-10-03, decision 8). The family had two members and a gap at the generative level; that is the gap. What remains open is not whether but how, and the open questions are listed below.

With %emit{ }, a backend stops being Ada and becomes a schema: a grammar whose input language is the hbnf notation (hbnf.hbnf) and whose rules match rule shapes, each with an %emit block naming the template that shape renders through. Scalar, Enum, Struct and List stop being an Ada enumeration and become four alternatives of a rule. That is META II's .OUT, one level up: output directives inside the syntax, which the HISTORY.md passage names as the part of META II that did not survive into the parser generators.

The semantics it needs are the ones already wanted elsewhere, which is the argument that this is a family extension and not a new feature:

  • Position-aware, so a block can sit between elements rather than only at the end of a rule — step 12's mid-sequence %action{} fix, which Lift already has the machinery for.
  • Per-alternative, which falls out of position-awareness: today one action serves a whole rule and discriminates on n->kind.
  • **A block may name a template, as shorthand for the code that renders it.** %emit{ c_struct } renders that template against the node; after 3b this is what the four backends do, just not sayable in a schema. Whether the family is %emit{ } only or %action{ } too is open — %scan{ } is not a candidate: a recognizer renders nothing.
  • Available to every backend, not C only, which %action{} is today.

What it must not break. The nine daemon parsers stay byte-identical and parse_config stays a drop-in for parse.y. A self-hosting path that cost the project its only hard external gate would be a bad trade; byteident is the gate here as everywhere.

And one ordering fact. This is second-order — a grammar whose input is grammars — so it needs hbnf.hbnf's own tree types to exist, which means 9b first. hbnf_schema.hbnf's mutually recursive entry/block is already the case in point: the backends refuse it today, and that refusal is why the interpreter still exists (9c).

What is still open, now that the member is settled. Four questions, and the first is the one that decides whether this feels native:

  1. How does a rule match a rule shape? A schema whose input is schemas needs to say "a rule that is one reference", "a rule whose alternatives are all literals", "a rule with a trailing repetition". A second-order grammar over hbnf.hbnf's own tree is the most BNF-native reading — those four are alternatives of a rule, and Scalar/Enum/Struct/List stop being an Ada enumeration. A pattern-matching sublanguage over Rule_Info would be more direct and less native, which is the trade.
  2. One schema per backend, or one schema with a language directive? language C already exists per file and decides which code blocks a backend takes; four schemas sharing an include is the obvious first answer and matches how obconf.hbnf is shared today.
  3. How does a block name a template? %emit{ c_struct } reads well, but a bare name inside a block that otherwise holds code is a second meaning for the same brackets. It may want its own spelling.
  4. Does %action{ } change, or only %emit{ } differ? Position and per-alternative behaviour are wanted for both (step 12). Running bottom-up after the parse is right for a binding and wrong for a one-pass translator, so the two members may legitimately differ on when, while sharing where.

And a standing alternative. Leaving the classifier in Ada and calling 13a the end is defensible — self-describing is a real property, and McCarthy's eval was useful without being a compiler. Reynolds' warning in the HISTORY.md passage applies here more than anywhere: a self-definition is trivial when the defining language is understood. The reason to do it anyway is Sitaker's — a metacircular compiler has to confront what an interpreter glosses over, and that confrontation is where the design errors show up. expr = term '+' term is the evidence: it was found by asking what META II could do that hbnf cannot, not by any test.

  1. Grammars for constrained decoding. Added 2026-10-27; not started. Like

step 11, an emitter that is not gated on anything above and can land between any two other steps. A language model that has to write text a program will parse (a tool call, a configuration, a protocol message) is more reliable when the decoder lets it choose only among the tokens that keep the output valid. Ubicloud measured the difference on Kimi K2.6 in vLLM: the expected tool-call schema 92% of the time without constrained decoding, 100% of the time with it, on the K2VV ToolCall benchmark, at "negligible performance overhead" (https://www.ubicloud.com/blog/fixing-tool-call-accuracy-in-vllm, 20 October 2026). What a decoder consumes is a grammar: llama.cpp reads GBNF, and XGrammar, which vLLM uses, reads an EBNF that follows GBNF "with many extensions, such as repetition ranges and macros". The emitter writes both from the lifted schema, so one HyperBNF file gives the program its parser and the decoder its grammar, and the program reads exactly what the model was allowed to write. Today the parser and the decoder's grammar are written separately and drift, the argument of step 11 again.

The mapping is mostly mechanical, because both formats are the same shapes under other names:

| hbnf | GBNF / XGrammar EBNF |

|---|---|

| a rule name = ... | name ::= ... |

| the first rule, or --root | root (the name both require) |

| concatenation | juxtaposition |

| \| | \|: see the catch below |

| [ x ] | x? |

| *( x ) / 1*( x ) | x* / x+ |

| n*m( x ) | x{n,m} |

| a literal | a double-quoted literal |

| %x41-5A, a class | [A-Z], and [^...] for a negation |

| a code point %x1F600 | \U0001F600 |

| ; comment | # comment |

| an instance of a hyperrule | an ordinary rule: the family is already expanded |

What does not map, stated plainly rather than papered over.

  • A decoder's alternation is not |. hbnf's | is ordered choice: the first branch that matches wins. A decoder reads a context-free grammar, where every branch is open. Every string the parser accepts the decoder accepts, but the decoder can allow a string the parser refuses, where a branch shadows a later one. hbnf already refuses a shadowed alternative when it reads the grammar, so the common case is the same language; the emitter names each rule where the two can differ.
  • Lookahead (&, !). Neither format documents a lookahead. The emitter refuses a grammar that uses one, naming the rule, unless the lookahead is rewritten as the character it looks at (the rewrite YAML's plain scalars use).
  • Numbers worked out while parsing (k in 0.., %spaces, %col) and the named context: not context-free, so a decoder cannot express them. Refused, with the rule named. A table of numbers that --expand-params can expand is context-free and is emitted.
  • Names. GBNF wants dashed lowercase words; XGrammar allows letters, digits, _, - and .. The emitter renames, and keeps a table from the new names to the old.
  • whitespace ws is skipped by the parser between a phrase rule's elements. The decoder has no such rule, so the emitter writes the skip into the grammar.
  • Keywords are matched as whole words by maximal munch. Without a lookahead the decoder cannot say "not followed by a word character", so a keyword that another token can begin with is a hole the emitter names.
  • Case-insensitive literals (%i) become a class for each letter.
  • Typed fields, actions, bit fields and hidden are out of scope: they shape the tree, and the decoder constrains text.

Gate: the grammars of corpus/json and corpus/toml emit, and each emitted grammar compiles in the decoders' own readers where they are installed (llama.cpp's grammar parser, XGrammar's Grammar.from_ebnf), accepts the corpus's good files, and refuses the bad files the parser refuses unless the emitter has named the rule where the two differ. Where no decoder is installed the gate compares the emitted text with a golden file. Whether the constraint raises a model's accuracy on a task is a measurement of the model and the decoder, not of the emitter, and is not claimed here.

Code-size optimization, deferred like 4f. The generated parser for a small wire grammar (the IRC message) is ~1,000 lines against ~280 hand-written, and the gap is structural, not a correctness cost. It is not a gate; it is recorded here so the shrink lands once the feature set is settled, against a generated-line-count figure taken then (4f's byte-identity gate is the cycle analogue). The five items, in payoff order:

  1. Emit only reachable rules. A grammar may include "common.hbnf" and reach three of its rules; every backend still emits a Parse_* function and type for every rule in every included file, dead or not. Reachability from the root — through includes, =/ extensions and overrides — decides what is emitted; the rest is never called. This is what lets a grammar keep its includes whole and stay small: a schema that includes common.hbnf and uses SP must not carry Parse_NUL … Parse_TILDE. The grammar is not expected to trim its own includes to work around the emitter.
  2. Optional is a nullable field, not a one-element vector. [ X ] currently becomes a package …_Vectors instantiation, an entry record and a subtype — three declarations to say "maybe". A nullable access or a discriminant is one.
  3. Repetition reuses one list type. Each *( X ) instantiates a fresh Vectors plus an entry record; a shared parameterized element list collapses that per-rule boilerplate.
  4. Emit the token layer only when a grammar tokens. A pure character-rule grammar still gets Token_Kind, Token, Token_Vectors, Line_Vectors and Parse_Tokens; gate that layer on the grammar using scanner actions/%scan, and emit a direct string reader otherwise.
  5. Share the per-rule save/backtrack boilerplate. Every Parse_* repeats save-position / when Parse_Error => P.Pos := Save; a single helper — or emitting the backtrack only where ordered choice or optionals actually need it — removes most of it.

Each item changes no parser's accept/reject behaviour, so the daemon corpus, e2e and byte-identity gates hold throughout; each is regression-tested by a generated-line-count figure, the way 4f is by cycles.

  1. Values at recognition: %emit{ } with $$. *Decided 2026-10-28 with the user; the reader, the analysis, the C backend and the JSON grammar are done.* A parser can build the structure its author wants as it reads, as yacc's actions do, instead of a tree that a later walk converts. The daemon bindings put their parse into the daemon's own structs and trees (TAILQ, RB), and JSON and YAML into the flat layouts the fastest parsers use (a tape of words; an array of fixed-size nodes with views into the input). A hand-written flat-tape JSON parser took 1.61 ms on the 2 MB file against 2.70 ms for the same code writing a typed tree, and 3.7 for the generated parser.

    Notation. %emit{ code } is the third member of the family (decision 8) and sits where %action{ } sits, at the end of a rule or between elements. A rule with a value says so after its name with ::, as Haskell does: object :: uint32_t = ..., and with parameters after them: member(M in 0..) :: uint32_t := .... The type is the words and *s up to the =, so peer :: struct ntp_peer * = ... needs no quoting; one { } block holds anything stranger, as raw C is held everywhere in the notation. :: followed by = stays the domain definition (level ::= 1..17) and := the hyperrule; a :: with a space after it is the type marker. The head stays one name; nothing in the hyperrule or the ALGOL 68 plan needs a multi-word head. In the code, $$ is the rule's value, set when the code sets it and kept for the emits that follow it in the rule, and each element is a C variable named after its rule: a token is a view (str), a rule with a value is that value.

    Timing. The code runs when its place in the sequence is reached. Inside the body of *( ... ) it runs once for each iteration, which is how a list becomes inserts into the author's own container. Nothing is stored for a rule that has a value: no struct, no list nodes.

    Everything combines with everything. A rule's result is its struct when it has no emit, its value when it has one with a type, and nothing when it has an emit and no type. A tree parent stores a child's value as a field; a stream parent reads a tree child as a variable. No kind of rule is barred from any position.

    Refusal, the one restriction, and why. An emit cannot be taken back, so it is safe only if nothing above it can retry past it. A grammar is refused, naming the rule and the overlapping alternatives, when an emit has an ancestor that can: an alternation whose alternatives can start alike (the fork analysis of decision 14), an option or repetition whose first set overlaps what can follow it, or a lookahead (!x, &x) that contains the emit. The analysis uses the lookahead sets the generator already keeps. It applies up the whole chain of ancestors, whatever kind of rule they are.

    What the analysis does today. It runs in HBNF_Compilable.Check on the rules as the backends see them. For every alternation that holds an emit, directly or through a rule it uses, the alternatives' first sets must not meet (an empty alternative counts as what may follow); for every option or repetition that holds one, its first set must not meet what may follow it, computed with the repetition turned off; an emit under a lookahead is refused, though the reader already allows only literals there. A built-in (word, int, str), a jet or a scanner action is taken to begin with anything, so a choice that starts with one and holds an emit is refused until the first sets of the built-ins are taught to the analysis. The reader's rewrite of *n( A S ) A into A *n( S A ) is skipped for a repeated part that holds an emit, because it would move the emit; the overlap is then reported.

    What the C backend does. A rule with an emit or a declared value is a function that runs its pattern as written and fills *out: no struct, no list node, and the reader makes up no rule for its groups or repetitions. Each element is a local named after its rule; the emit code runs only in the first (quiet) pass, so the pass that reads a failure again runs none. Context operations (%spaces, %col, %num, lookahead, guards) are written by the sequence code, one element at a time. A choice whose alternatives begin with different ASCII characters is a switch on the first character in the first pass (the second pass still tries them in order, so the messages are the same). Rust, Zig and Ada refuse an %emit, naming the rule. The C arena maps chunks past the first and goes back for the iteration that ends a list; a list stores only its head. Children that are full tree rules have not been tried.

    Measured. corpus/json/json-tape.hbnf writes a tape of 64-bit words, one for each value and key. On the 2 MB document, pinned to cpu 5, one cold parse: 1.8 ms against simdjson's 1.7 (best of five; in an interleaved run of 25 simdjson's median was 2.13 against 1.82 for the tape, its minimum 1.63 against 1.80), in 5 MB against simdjson's 15; the generated tree parser takes 2.1 and RapidJSON 5.4. The steps that mattered, by size, on the tape: no tree took the cold parse from 3.95 to about 3.4 ms; first-character dispatch and the cheaper skip_ws to about 2.8; a tape sized from the input, on a 2 MiB boundary with a huge-page hint, to 2.0; the generator round after it (quiet and loud bodies for a rule that runs emits, a fast path for a quoted token, the stack guard on the rules called least, the scanner going straight to the byte its wide step stopped on) to 1.8, from 37.9M instructions for the parse to 29.6M (a hand-written parser of the same layout takes about 21M). Inlining the scanners made it slower, and a stack guard of a different form compiled to the same code. The memory finding was worth more to the tree parsers: the C arena maps chunks past the first on a huge-page boundary and does not clear them, which took the YAML tree's page faults from 8,824 to 1,061 and its parse from 22 to 15 ms and then, with the string fast path, to 14 (rapidyaml: 16; in an interleaved run of 25 on cpu 5, 14.3 against 15.9 at the median), the JSON tree from 3.4 to 2.1 and the TOML tree from 9.2 to 6.4. What a tape buys over a tree is therefore smaller than the first measurements said: 1.8 against 2.1 ms for JSON.

    Order of work. Done: the reader (the type after the name; %emit blocks in every position); the refusal analysis, with its tests; the C backend; JSON as the first grammar, checked against Python's json and measured; rollback { } (the grammar names what its emits change and the generated code puts it back at every retry, so a retry past an emit is no longer refused); the TOML and YAML tape grammars (corpus/toml/toml-tape.hbnf, corpus/yaml/yaml-tape.hbnf, on the runtime/hbnf_tape.h tape), checked against tomllib and the YAML test suite and measured (step 17). Not done: the daemon bindings' action blocks as emits (their lists use layout tailq), and an %emit in the Rust, Zig and Ada backends.

  3. Layouts: one grammar, several data structures. *Added 2026-10-29 with the user; built: layout tape, tailq and rb, C backend only. --layout=ast|tape|tailq|rb|NAME (or layout NAME in a grammar) names one; ast is the default.* A grammar says which data structure its parser builds, and the rest follows from the grammar: layout ast (today's, the default), layout tape, and options on a list rule for the containers a program already has, tailq (sys/queue.h) and rb (sys/tree.h, keyed on a field). The three tape grammars (json-tape.hbnf, toml-tape.hbnf, yaml-tape.hbnf) were written by hand, and the hand-written %emit blocks in them are what a layout would write.

    How. A layout is a rewrite of the rules before generation, as Lift is: it inserts the %emit blocks of step 15, with the types and the rollback the layout needs, and the generator that exists does the rest. A tape layout makes an opener and closer for each rule that holds fields, a text entry for each token, and nothing for a literal, a hidden rule, a pure choice or a list wrapper (the children just follow): the tree, laid flat, with rule numbers or %labels as tags. tailq and rb give a list rule a container in the daemon's own struct, so the obconf bindings need neither layout_ops (which cannot say a key) nor the intermediate tree and the action that copies it.

    What stays %emit. What the tree never had: a different meaning (true and false as tags, a number converted), a different shape (YAML's explicit null for an absent value, one mapping around a flow pair), a computed value. The hand-written tape grammars stay as the references the derived tape is measured against, on the three formats, before it is made the default for C.

    What the tape layout does, built. layout tape in a grammar, or --layout=tape, rewrites the rules in HBNF_Grammar.Tape_Layout, at the start of Lift (so the language checks have seen the grammar as written). Every phrase rule becomes a function that yields a value and builds no struct. A rule that holds fields is opened where it begins and closed where it ends, with its rule as the tag; a token (a character rule a phrase names, a rule that is one literal, word) is one entry with its text; an enum rule is one entry with its value; int is one entry with its value (40 bits); a literal, a hidden rule, a rule that is a choice of other rules or one other rule write nothing, so a choice or an alias adds no node. The tags are an enum and a name table in the generated prologue, rollback { tape_n } is implied, and the tape is runtime/hbnf_tape.h's (the generated C includes it, so it is compiled with -Iruntime). Not yet: str, bool, flag and the fixed-width numbers (nothing is written for them), a left-recursive rule (refused), more than 255 kinds of node (refused), a Rust, Zig or Ada backend. tests/layout.sh checks it: the exact tape of a small document; for every good JSON file the same objects, arrays, members, strings, numbers and literals as Python finds; TOML against tomllib and YAML against the test suite, with the plain grammars and --layout=tape.

    Closing the gap to the hand-written tape. The first derived YAML tape wrote 1,048,705 words for the 2 MB document where the hand-written one writes 218,639 (JSON: 306,786 against 214,287; TOML 513,113 against 323,340), found by counting the entries of each kind. Three changes, none of them emit code: (1) a rule that can only ever hold one node of its own, found by going round the grammar until nothing changes, writes no node, its child stands for it (a rule that holds nothing written and matches no literal text, a gap or a lookahead, writes nothing); (2) a rule whose written parts are all text tokens, with no blank skipped between its elements, is one entry with the text of the whole match (YAML's plain scalar over several lines); (3) two hints in the grammar, hidden (existing: SP WSP DQUOTE in yaml-tokens.hbnf, newline in toml-tokens.hbnf; which also take those fields out of the tree) and flat, for rules that keep their children and write no node (flat ikey mapent mval inl ... in yaml.hbnf; the tree ignores it). With them the derived YAML tape is 220,053 words, the hand-written one's size within 1%, and the same structure for a small document (tests/layout/small-yaml.expected); TOML's is 418,227 (it keeps the dotted key as a node) and JSON's unchanged (a node for each member). Cold, interleaved on cpu 5: JSON 2.12 ms the tree, 1.79 the hand-written tape, 1.96 the derived; TOML 6.91, 5.00, 5.03; YAML 16.4, 11.5, 11.4 (a slow phase of the machine; the order is what holds).

    Measured, the 2 MB documents, cold, interleaved on cpu 5, in a noisier phase than the figures above (read the three together): JSON, the typed tree 2.58 ms, the hand-written tape 2.15, the derived tape 2.39; TOML 9.07, 7.05 and 7.26; YAML 18.4, 10.6 and 13.9. The derived tape needed no %emit and is within 10% of the hand-written one on JSON, within 3% on TOML, and 30% behind on YAML, which writes more nodes (12.9 MB against 5.6; an opener for every rule that holds fields where the hand-written tape has one for each mapping and sequence). The reserve of tape_reserve is a quarter word a byte for this reason: the first, an eighth, made the derived JSON tape overflow its room and grow, which cost a third of its time.

    Operations, and rollback with them. A layout is a set of operations, and rollback is one of them: each layout says in its own terms how to take a mark and how to put back to it. The layout_ops { head { } entry { } ... } block (it was listops, and every grammar that had one now says layout_ops; layouts/tailq/layout.hbnf is the daemons') is the list-shaped part of this, and layout tailq reads that file. A layout is a directory, layouts/NAME/, holding layout.hbnf (the operations, the prologue that includes the layout's header, the epilogue) and the C of the layout (hbnf_NAME.h) with its test; the directory is found by --layouts=DIR, $HBNF_LAYOUTS, else beside the template directory. The operations a layout needs beyond them (mark, reset, and for a layout that holds entries back, commit) are added beside them when a layout needs them. A grammar that names no layout but a state to put back (rollback { tape_n }, step 15) is the shortest layout there is: its mark is the value of each lvalue and its reset assigns it again. The built-in layouts supply theirs, and a grammar may define its own.

    The rollback problem. rollback (step 15) is one store for state that is a stack: a tape put back to where it was. A TAILQ is nearly as cheap (unlink back to a saved tail). A red-black tree is not: undoing insertions means deleting keys. So an rb layout collects the entries of a list on a stack while the parse can still retry past them, and builds the tree when the enclosing rule has succeeded, or keeps an undo log. Which, is decided when it is built.

    Order. After the Haskell comparison (the rig is bench/haskell.sh), the tape layout first, since its references exist; then tailq (built, as layouts/tailq: the tree whose lists are the daemons' TAILQs); then rb (built, as layouts/rb: the tree whose lists are OpenBSD's red-black trees (RB_* of <sys/tree.h>, the real file, v1.31, kept in layouts/rb/sys/ for hosts without one) of the element's own, in the order of a key the grammar names, so the daemons' macros work on them; insert only, so a branch that gives up leaves nothing in it to undo; a repeated key is dropped and the first stays. The layout operations are given the tree's name and the element's tag, and generate writes the comparison and RB_GENERATE once for each list. It is not the daemons' own tree, whose element and compare are the daemon's, so unwind's force list stays an action). C backend only. Gate: the tape derived from json.hbnf, toml.hbnf and yaml.hbnf is measured against the three hand-written ones, and the obconf daemons' byte-identity tests pass unchanged.

  6. Grammars for COBOL, ALGOL 68 and C++. Added 2026-10-31 (the user); COBOL begun 2026-10-31 (corpus/cobol/: free format, checked against cobc on a few programs of its own and on the programs of GnuCOBOL's test suite, tests/cobol-scan.sh), ALGOL 68 and C++ not started. What makes COBOL hard is not its syntax but what surrounds it: COPY chains (a preprocessor's work, so with the C preprocessor item), fixed-format columns (a ws scanner can skip the sequence area and read the indicator column, since it can look back to the line start; the continuation of a literal is the hard part), decades of dialects, and a type system in the PICTURE and USAGE that a parser must keep as written. One grammar for each, written to read as much like the pure BNF of the language's own standard as the notation allows: compact and idiomatic, a rule for a production, the production's name, and no lexer tricks beside it. This is the test of the claim in the README that a grammar can carry a language that a yacc file can only carry with hacks. ALGOL 60 was done first, as the Report's BNF (corpus/algol60/). What hbnf already has for the ambiguity these three languages carry is ordered choice, the union /, parameterised rules, back-references, context sets and the local, detected fork (decision 14, --forks); the plan for ALGOL 68 above says which of them stand for the W-grammar's machinery. Full GLR is allowed here (the user, 2026-10-31), for the ambiguity those do not cover. The policy is that nothing is paid for unused: a grammar that does not need GLR gets the parser it gets today, with no stack, no table and no cost per token; the machinery is generated only for a grammar that asks for it. Still to settle, with the user before any of it is built (a syntax change is shown first): how a grammar asks for it, what a parse that is ambiguous returns (one tree by a stated rule, or all of them), and what the other backends do (refuse, as they do for %emit, or implement). The order of the three is not fixed; C++ leans on the C family (corpus/c/) and the typedef context of step 16.

    A preprocessor in the same grammar (the user's question, 2026-11-02; an idea, not decided). COPY, REPLACE, #include and #define can be applied as the parser goes, instead of in a pass before it: a source stack. Reaching COPY name. or a macro call pushes the other text (a copybook, a macro's expansion) as the current input, the same rules go on reading it, and its end pops back. A REPLACE or a #define is a fact (the pattern and its replacement, live until REPLACE OFF or #undef) that the scanner consults at each token; #if is a live/skipped region. Facts and the stack are put back when a guess is given back, as the typedef sets are. It handles what a separate pass handles badly (a macro that expands to half a declaration), and a program with no preprocessing pays nothing. Every position is then a chain of origins, (source, offset) with the place that pushed it, so an error or a tree node can be reported as gcc does (in expansion of macro M, at a.c:3, copied from X.cpy by prog.cob:12). Open: how the memo of a speculative parse keys positions that come from different sources, and where REPLACE's pseudo-text matching (a token sequence, not a name) sits in the scanner. Sketched with the island and switch of CONTEXTS.md.

    Generator bugs found while working on the COBOL grammar (2026-11-02), and fixed. (1) A lookahead (! or &) inside the character-level ws rule (ws = ... | "$" !picture-start *~( CR | LF )) stopped generation with `raised CONSTRAINT_ERROR : hbnf_compilable.adb:481 discriminant check failed. The parser skips ws by running a scanner, so ws` and what it reaches are now rules of characters even where they hold a lookahead: the scanner (Char_DNF) has a Look atom, and each backend writes a function for what the lookahead looks at (look_...), read a character at a time and building no tree.     A design idea, not decided (the user, 2026-10-31). A grammar that reads one language can also say how a rule is written out in another, so that it translates: ALGOL's begin statements end comes out as C's { statements }, and a keyword comes out in capitals. A rule is then one of three things: a transformation rule (it is written out in a different form from the one it was read in), a rule that emits code (its output is a template), or a rule that runs code that emits code (host code builds the output). The point is to keep the productions themselves idiomatic and as close to pure BNF as the notation allows, with what a rule is written out as set beside it and not woven through it. What exists: the writer (--writer), which writes a tree back in the syntax it was read in, %emit at recognition time with $$ (step 15), %action over the finished tree, bottom-up, and the layouts, which turn a tree into a tape. What does not: an output form per rule, and a second syntax to write in. To settle, with the user and with the notation shown first: where a rule's output form is written (beside the production, keyed by its name, or in a section of its own), how a token is rewritten (keyword case), and which backends refuse it. As everything here, a grammar that uses none of them pays for none of them.
