# RFC 3986, Appendix A: Collected ABNF for URI

`rfc3986-1.bnf` is the whole appendix, verbatim; its only addition is the `include`
that supplies RFC 5234's `ALPHA`, `DIGIT` and `HEXDIG`.  `rfc3986-1.hbnf` is
the same rules as hbnf reads them.  `<id>.vectors/` holds 23 rules' inputs
(`scheme`, `host`, `IPv6address` and the rest of its closure, the path forms,
`URI`); `host` and `IPv6address` run in all four backends, the rest in C.

## What hbnf says to the RFC's text

The whole appendix compiles as written except two places.  `/` is taken
wherever ordered choice, in some order of the alternatives, accepts the same
language, and the reader writes the choice in that order: between
one-code-point alternatives (`unreserved`, `sub-delims`, `pchar`), in character
rules, whose scanner takes the longest alternative (`dec-octet` in the RFC's own
order), and between longer alternatives, however far into the input they
differ (`hier-part`, `ls32`: `h16 ":" h16` against `IPv4address`, told apart at
the `:` or the `.`; `IPv6address`'s nine alternatives; `URI-reference`).

What hbnf refuses is a union that needs backtracking, and it says so, and why,
and what to write:

    hbnf: rfc3986-1.bnf:31:28: `/` is ABNF's union, and here hbnf cannot compile it
      ABNF tries every alternative and goes back if what follows does not fit.
      hbnf chooses once and does not go back, so it writes a union as an ordered
      choice in whatever order gives the same language; here no order does:
      `IPv4address` only matches text `reg-name` also matches, so as an
      alternative it adds nothing: leave it out
      host          = IP-literal / IPv4address / reg-name

(`path`, a documentation rule the grammar does not use, is refused the same
way: `path-abempty` matches whatever `path-absolute` and `path-empty` do.)  And
(`path`, a documentation rule the grammar does not use, is refused the same
way: `path-abempty` matches whatever `path-absolute` and `path-empty` do.)
`path-empty = 0<pchar>` needs nothing: `<pchar>` names the rule `pchar`, so it
reads as `0pchar`, zero of them.

**`IPv6address` compiles as written, and correctly.**  Its left parts are
`[ *1( h16 ":" ) h16 ]`: in ABNF the optional `h16 ":"` is given up when the
`h16` after it fails.  hbnf's repetitions are greedy and keep what they take, so
read literally it would refuse `1::2`.  The reader writes `*n( A S ) A` as
`A *n( S A )`, which is the same strings with nothing to give back, so the RFC's
text parses what the RFC means.  (Where hbnf cannot do that rewrite and the
difference would matter, it says so: "this repetition is matched greedily,
unlike ABNF's", with the way to write it.)

## The fixed-up version

`/` throughout, as the RFC has it, except:

- **`host`**: `IP-literal / IPv4address / reg-name` is ambiguous (a dotted quad
  is also a `reg-name`; RFC 3986 section 3.2.2 says so).  `|` commits to
  `IPv4address` and takes `1.2.3.4` out of `1.2.3.4.5`, then fails where the
  RFC's union goes on to `reg-name`.  `host = IP-literal / reg-name` accepts the
  same language; an address parses as a `reg-name`.
- **`path`** is not repaired, and has no vectors.

`IPv6address`, `ls32`, `URI-reference`, `dec-octet` and `IPvFuture` are the
RFC's own: the first four by the reader's choice of order and its rewrite, the
last because in a grammar with no `word` a letter-led literal is the characters
it spells, which `sensitivity string %i` makes `v` or `V`.

## Not covered

`URI-reference`, `relative-ref`, `relative-part` and `path` have no vectors.
`URI-reference` (`URI / relative-ref`) compiles as written; their overlap (a
relative reference whose first segment looks like a scheme) is what RFC 3986
section 4.2 spends a paragraph on.  `URI` and `absolute-URI` are tested.
